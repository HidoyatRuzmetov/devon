# ADR-000: Security baseline is OWASP ASVS 5.0 Level 2 plus `agentic/HARDENING.md`

- **Date:** 2026-09-06   **Status:** accepted
- **Deciders:** wp-architect + wp-security   **Epic:** EPIC-000

## Context
The platform holds employee personal data on a ministry server under Uzbekistan's data-localisation law (`docs/01-research/uzbekistan-context.md` §42; `auth-permissions-security-compliance.md` §8–9). It is owned by a state body, which per `uzbekistan-context.md` (gap-fill §299) very likely triggers mandatory state cybersecurity expertise before production rollout. We need one named bar so that "is this secure enough" stops being a per-epic argument. ASVS 5.0 was released 30 May 2025 and has a Russian translation, which matters for briefing local reviewers.

## Decision
The security bar is **OWASP ASVS 5.0 Level 2**, operationalised as `agentic/HARDENING.md` H1–H30. Level 1 is insufficient (we hold citizen-adjacent employee PII); Level 3 is out of scope (no national digital-ID and no payment integration — decision 10). Every epic satisfies the applicable HARDENING items (I-9a) and verifiers cite item ids in findings; EPIC-014 executes the full list with measurements. In EPIC-000 the applicable items are H1.1, H1.2, H1.3, H1.4, H1.7, H1.9, H1.10, H1.11, H1.13, H1.15, H1.16, H3.3, H3.7, H7.3, H16.1, H17.1, H18.1, H21.1, H22.1.

## Consequences
- Positive: one citable standard for the ministry's IT security office; the checklist is machine-adjacent (most items map to a gate), so compliance is evidenced rather than asserted.
- Negative / debt accepted: no WAF, no SBOM signing and no incident-response runbook in EPIC-000. Uzbek law imposes **no breach-notification duty** (`auth-permissions-security-compliance.md` §G5, confirmed) so an incident runbook is an internal-standards choice, deferred to EPIC-014 with that fact stated rather than assumed.
- Migration / rollback path: none needed — this is a policy, not code. Raising to L3 later is additive.

## Alternatives considered
- ASVS Level 1: rejected — too low for a system holding personal data.
- ISO 27001 as the primary frame: rejected — it is an ISMS standard about organisation and process, not a checklist a delivery loop can gate on; kept as the mapping target for a future audit.

# ADR-001: pnpm + Turborepo monorepo, `@devon/*` scope, exact version pins, script parity

- **Date:** 2026-09-06   **Status:** accepted
- **Deciders:** wp-architect   **Epic:** EPIC-000

## Context
`agentic/gates.json` is hook-protected and names packages literally: `pnpm --filter @devon/db migrate:verify`, `pnpm --filter @devon/web test:e2e`, `pnpm --filter @devon/web test:a11y`, `pnpm --filter @devon/ai evals`, plus `pnpm -w --if-present security:scan` and `perf:check`. Four gates use `pnpm -r --if-present`, which passes vacuously when no package defines the script — AC-14's disproof calls that out by name. TECH-SPEC §1.2 pins every library exactly (no `^`) with provenance checks in CI.

## Decision
One pnpm workspace with Turborepo. Package scope is **`@devon/`** and the names `@devon/db`, `@devon/web`, `@devon/ai` are fixed by `gates.json`, not by preference. Every workspace package declares `typecheck`, `lint`, `test:unit`, `build` even when the body is trivial; the workspace root declares `security:scan` (Semgrep OWASP + Trivy fs) and `perf:check` (Lighthouse CI + k6). `packages/config/test/workspace-scripts.test.ts` reads `pnpm-workspace.yaml` and fails the `unit` gate if any package is missing one of the four — so the `unit` gate is what proves the other gates are not vacuous. All dependency versions are exact, `packageManager` pins pnpm for corepack, and `node setup.mjs` exists at the repo root so a machine with only Node can bootstrap.

## Consequences
- Positive: `--if-present` can never silently no-op; renaming a package is a gate failure, not a mystery; a clean clone works with Node and Docker alone.
- Negative / debt accepted: trivial script bodies in packages that have nothing to build; Renovate must be self-hosted and configured to keep exact pins rather than ranges.
- Migration / rollback path: package renames require a `gates.json` change, which is an escalation, not an edit — so renames are effectively frozen. Accepted.

## Alternatives considered
- Nx: rejected — heavier and more opinionated than a 9-package repo needs.
- npm/yarn workspaces: rejected — `gates.json` commands are pnpm-specific.
- Loosening `--if-present` by editing `gates.json`: refused — gates are never weakened by an agent (PROTOCOL §3).

# ADR-002: Tenancy is `department_id` + Postgres RLS, with a four-class table registry

- **Date:** 2026-09-06   **Status:** accepted
- **Deciders:** wp-architect + wp-security   **Epic:** EPIC-000

## Context
`CLAUDE.md` says "every table has `tenant_id`". `agentic/INVARIANTS.md` I-1 and TECH-SPEC §3 say `department_id`. Decision 3 says there is no ministry layer: one instance = super admin + departments, and departments never see each other (I-8a). `backend-architecture-and-multitenancy.md` §4 recommends shared-schema + RLS with per-tenant deployment as the political escape valve, and §2 warns about two RLS foot-guns (sub-select races under READ COMMITTED, and global unique constraints leaking cross-tenant existence). §A8 warns that a session-scoped `SET` under PgBouncer transaction pooling leaks tenant context across requests. AC-10 requires that a table without `department_id` and a policy fails the migrate gate — which means "which tables are department-owned" must be machine-readable.

## Decision
The tenant column is **`department_id`** and there is no `tenant_id` anywhere. Per-ministry isolation is a deployment topology (one Compose stack per ministry, same schema, same policies), never a code fork. Every table is classified in `packages/db/src/tenancy.ts` as one of `tenant_root` (`app.departments`, policy on `id`), `department_owned` (`department_id not null` + RLS + a policy referencing `app.current_department_id()` + an index leading with `department_id`), `user_owned` (`user_id` + RLS + owner-only policy, with **no** role escape for head or super admin — I-1), `global` (explicitly allow-listed with a written justification), or `audit`. The migrate gate asserts that every base table in `app` and `audit` is classified and that each class's invariants hold; an unclassified table fails. Context is set with transaction-local `set_config('app.<k>', $v, true)` as the first statement of every transaction, issued only by `withContext()` in `@devon/db`; the `Pool` is not exported and the raw-query escape hatch asserts the GUCs are set. `devon_app` is **not** the table owner (`devon_migrator` is) and `FORCE ROW LEVEL SECURITY` is set anyway. Policies compare a column to a GUC and contain no sub-selects. Every uniqueness constraint on a department-owned table is scoped `(department_id, …)`. Super-admin cross-department reads go through `view_as`, which sets the same `app.department_id` and additionally sets `app.view_as=true`, which every write policy denies — there is no bypass role and no policy exemption.

## Consequences
- Positive: cross-department isolation is enforced by the database even if application code is wrong; adding a table forces an explicit tenancy decision; an unset context returns zero rows rather than everything; PgBouncer transaction pooling is safe.
- Negative / debt accepted: `global` is a real category and will be argued about; classifying `app.departments` as `tenant_root` rather than `department_owned` is a fourth concept the reader must learn; the advisory that policies contain no sub-selects will eventually be inconvenient (the escape is a `SECURITY DEFINER` helper, permitted by the migration linter only with that marker).
- Migration / rollback path: purely additive. If a future ministry demands physical separation, the answer is a second Compose stack with the same migrations, not a schema change.

## Alternatives considered
- Schema-per-department: rejected — N migrations and drift past ~30 tenants (`backend-architecture-and-multitenancy.md` §4), and this instance is expected to hold 200.
- Application-layer filtering only: rejected — one forgotten `where` leaks personal data; RLS is the backstop that survives a wrong query.
- A `tenant_id` column aliasing `department_id`: rejected — two names for one thing is exactly the confusion this ADR exists to remove.

# ADR-003: Built-in login with server-side sessions; Postgres is the sole revocation record; `SameSite=Lax`

- **Date:** 2026-09-06   **Status:** accepted
- **Deciders:** wp-architect + wp-security   **Epic:** EPIC-000

## Context
Decision 4 (frozen, TECH-SPEC §19) chooses built-in login/password with server sessions and rules out OneID and Keycloak, against `auth-permissions-security-compliance.md`'s primary recommendation. TECH-SPEC §2.1 describes sessions as "Postgres row + Valkey". AC-13 requires that a cookie captured before logout replays as 401 and that the cookie carries HttpOnly, Secure and SameSite=**Lax**; its disproof explicitly names "session state held only in the client or only in Valkey with no server-side revocation record". OWASP and the research recommend `SameSite=Strict`.

## Decision
Sessions are a row in `app.sessions` holding `sha256(token)`; the raw 32-byte CSPRNG token exists only in the cookie. **The Valkey session mirror is deferred out of EPIC-000**: every cache design either leaves a window in which a revoked cookie still authenticates (failing AC-13) or adds distributed invalidation to a foundation epic. Authentication is one indexed lookup per request inside the transaction the request already opens; Valkey is used only for rate limits. A mirror may be added later, gated on a measurement: p95 session lookup > 5 ms or sustained > 500 rps.

Cookie: name `devon_sid`, `HttpOnly; Secure; SameSite=Lax; Path=/`, no `Domain`. **Lax, not Strict**, because `/join/:key` invite links (EPIC-002) and Telegram deep links (EPIC-007) are cross-site top-level GET navigations that must carry the session; under Strict the invite flow — the product's main growth path — silently drops the user at a login screen. Compensating controls: double-submit CSRF token (non-HttpOnly `devon_csrf` cookie, `X-CSRF-Token` header, HMAC-bound to the session) required on every unsafe method, plus an `Origin`/`Sec-Fetch-Site` check, plus no state-changing GETs anywhere. `Secure` is set unconditionally; `http://localhost` is a secure context in Chromium and Firefox, which are the e2e browsers for this epic. Sliding 12 h idle / 30 d absolute; session id regenerated on login and on privilege change; `POST /auth/logout` sets `revoked_at` and writes an audit row in one transaction.

## Consequences
- Positive: AC-13 is satisfied by construction, not by timing; there is exactly one place a session can be revoked; one fewer stateful dependency in the foundation.
- Negative / debt accepted: one extra indexed Postgres read per authenticated request (measured, budgeted, and cheap because the transaction is already open). `SameSite=Lax` is weaker than the research's recommendation and puts real weight on the CSRF token and the Origin check; both are unit-tested and a Semgrep rule fails any state-changing GET handler. No SSO, no AD federation, no passkeys — a real capability gap owned by decision 4, revisitable only by changing that decision.
- Migration / rollback path: adding a Valkey mirror later is additive and behind a flag. Adding an upstream IdP later means adding an `external_identities` table and a login route; the session model is unchanged.

## Alternatives considered
- Keycloak (the research's recommendation): rejected by frozen decision 4. Recorded so the cost is visible: we now own password storage, lockout, MFA and reset ourselves.
- Stateless JWT: rejected — no server-side revocation, which AC-13's disproof names directly.
- `SameSite=Strict`: rejected — breaks the invite and Telegram entry paths, which are the product's adoption mechanism.

# ADR-004: `audit.events` is append-only, hash-chained, and serialised by an advisory lock

- **Date:** 2026-09-06   **Status:** accepted
- **Deciders:** wp-architect + wp-security   **Epic:** EPIC-000

## Context
I-5a requires that the application role hold INSERT and SELECT only, that UPDATE/DELETE/TRUNCATE be revoked **and** trigger-blocked, that rows be hash-chained, and that the chain head be anchored nightly outside the database. AC-9 additionally requires that tampering with one row's payload as a superuser makes verification report **exactly that row**. `auth-permissions-security-compliance.md` §8 gives the same shape (append-only table, no UPDATE/DELETE grants, periodic hash-chaining, access to the log itself logged).

## Decision
A separate `audit` schema. `devon_app` holds exactly `{INSERT, SELECT}`; UPDATE, DELETE, TRUNCATE, REFERENCES and TRIGGER are revoked, **and** `BEFORE UPDATE`, `BEFORE DELETE` (row-level) and `BEFORE TRUNCATE` (statement-level) triggers raise `42501`. Both layers ship because AC-9's disproof rejects either one alone. `row_hash = sha256(prev_hash || audit.canonical(row))` where `canonical()` covers only content columns (never `seq`, `prev_hash`, `row_hash`), computed in a `BEFORE INSERT` trigger that first takes `pg_advisory_xact_lock(hashtext('audit.events'))` so concurrent inserts cannot read the same `prev_hash`. `audit.verify_chain(from, to)` recomputes each row's content hash **and** checks linkage, returning the first offending `seq` and which of the two checks failed — so a payload edit reports that exact row, and a removed row reports the successor. Audit rows are buffered on the `Tx` and flushed inside the same transaction as the domain write (I-5). A nightly job appends `{head_seq, head_hash, at, pg_version}` to a file on a separate volume and inserts an `audit.anchors` row. No retention job may touch the `audit` schema; the sweep's table allow-list is unit-tested. A migration that alters `audit` grants is refused by the migration linter (I-5a says such a migration is SEV1).

## Consequences
- Positive: tamper-evidence that survives a compromised application role; a single chain gives a single, simple verification story; the two layers mean neither a grant mistake nor a trigger drop is sufficient on its own.
- Negative / debt accepted: **audit inserts are serialised instance-wide.** At the target scale (200 departments × 300 people, ~10–50 audit writes/s, lock held for microseconds) this is comfortably fine, and EPIC-014's k6 run measures it. Canonicalisation depends on Postgres's `jsonb` key ordering, so the anchor records the server version; a major upgrade that changed it would surface as a verification failure with a known cause rather than silently.
- Migration / rollback path: if the lock ever binds, the named fallback is per-`department_id` chains — weaker global tamper-evidence, better throughput — introduced as a new chain family from a marked `seq` forward, never by rewriting history. A restore from backup appends an `audit.anchors` row naming the restore point so a chain gap has a documented cause.

## Alternatives considered
- Application-computed hashes: rejected — a bug or a bypassing code path breaks the chain silently; the trigger holds for every writer.
- WORM storage / external append-only log as primary: rejected for EPIC-000 as premature infrastructure; the nightly anchor gives most of the benefit at a fraction of the cost.
- Per-row signatures instead of a chain: rejected — signatures detect edits but not deletions; a chain detects both.

# ADR-010: Design tokens as DTCG → Tailwind v4 `@theme`, Palette B, self-hosted subset fonts

- **Date:** 2026-09-06   **Status:** accepted
- **Deciders:** wp-architect + wp-designer   **Epic:** EPIC-000

## Context
`DESIGN.md` §2 fixes Palette B in OKLCH with hex conversions marked as regenerable, a per-tenant override surface limited to `--color-primary*`, `--color-sidebar*`, logo and display name via `data-tenant`, and a typography rule that is a correctness requirement rather than taste: `Oʻ`/`Gʻ` use U+02BB and `ʼ` uses U+02BC, and fonts "must not be subset below the Spacing Modifier Letters block". AC-6 fails on tofu, on a straight quote, or on a glyph rendering in a visibly different typeface. H8.2 and the data-localisation posture forbid third-party asset hosts.

## Decision
OKLCH values in DTCG JSON are the source of truth; Style Dictionary generates the Tailwind v4 `@theme` block and the hex fallbacks at build time — hand-edited hex is a lint failure. Dark mode is a separate token set (lightness-tint elevation), not an inversion. Per-tenant theming is exactly the four variables above, applied from `data-tenant` on `<html>`; nothing else is themeable. Fonts (IBM Plex Serif display, Inter UI, IBM Plex Mono) are **self-hosted woff2 subsets** whose `unicode-range` covers Latin, Latin Extended, **U+02B0–02FF (Spacing Modifier Letters)**, **U+0400–04FF and U+0500–052F (Cyrillic + Supplement)**, with `font-display: swap` and only the critical faces preloaded. Two automated checks ship with the tokens: a `unicode-range` coverage test over the built woff2 files, and a rendering test that compares the advance width of `Oʻ Gʻ ʼ ў ғ қ ҳ` in the shipped face against a forced-fallback face — equal widths mean substitution and fail. A Storybook glyph page is the human-readable artefact. Status is never colour-only: every status chip carries a label and, on boards, a leading glyph.

## Consequences
- Positive: Uzbek and Cyrillic correctness is a test, not a review opinion; no external font request, so nothing leaves the ministry server; per-tenant theming cannot drift into a per-tenant redesign.
- Negative / debt accepted: larger self-hosted font payload than a Latin-only subset; Style Dictionary is an extra build step; the narrow theming surface will eventually be asked to widen (the answer is a new ADR, not an ad-hoc variable).
- Migration / rollback path: tokens are CSS variables — reverting a palette change is a token-file revert with no schema or API impact.

## Alternatives considered
- Google Fonts / any CDN: rejected — leaks request metadata off the ministry server and breaks air-gapped operation (H8.2).
- Mantine or another pre-styled library: rejected (`frontend-architecture-and-sync.md` §D) — its look fights the "ownable, distinctive" goal; shadcn-style copy-in components on Base UI/Radix keep the accessibility floor and the ownership.
- Hex as the source of truth: rejected — OKLCH is what makes the dark-theme re-tuning and the 8-hue categorical unit palette derivable rather than hand-picked.

# ADR-011: Pause and wipe live behind a loopback-only, signed-command host sentinel; EPIC-000 ships `noop` only

- **Date:** 2026-09-06   **Status:** accepted
- **Deciders:** wp-architect + wp-security   **Epic:** EPIC-000

## Context
Decision 16 and TECH-SPEC §11 require a super-admin pause switch and a wipe switch that removes this project and nothing else. The application cannot delete itself, so a host-level service is needed. AC-15 constrains EPIC-000 tightly: signed no-op only, from 127.0.0.1 only, valid, unexpired and non-replayed, not bound to 0.0.0.0, and **no wipe or pause execution path in this epic**; the disproof explicitly includes a Docker bridge address as a non-loopback caller.

## Decision
`infra/sentinel` is a dependency-free Node service run by systemd on the host (Node is already an AC-1 prerequisite; adding Go would add a toolchain for ~200 lines). It calls `listen({ host: '127.0.0.1' })` — never `0.0.0.0` — **and** independently rejects any peer whose remote address is not `127.0.0.1`, `::1` or `::ffff:127.0.0.1`. Commands are ed25519-signed over canonical JSON (sorted keys, no whitespace) of `{v, command, nonce, issued_at}`; the public key lives only in `/etc/devon/sentinel.conf` (0600, root) and the private key never enters the repo, the app image or any `.env`. Verification order is fixed: peer → size (≤4 KiB) → parse → signature → freshness (|now − issued_at| ≤ 60 s) → nonce unseen (persisted file, retained 300 s, strictly longer than the freshness window) → command allow-list. **The allow-list in EPIC-000 contains `noop` and nothing else**, and a unit test greps the built artefact for `rm`, `unlink`, `rmdir`, `docker`, `volume` and fails if any appears — so "no destructive path exists" is a test result, not a claim. Every request outcome writes one line to `/var/log/devon-sentinel.log`. Pause (maintenance mode) is application state in `instance_settings` plus a Caddy fallback page and never touches the sentinel. The wipe command, the console ceremony (phrase + password + 2FA + 60 s countdown) and the host CLI arrive in EPIC-013.

## Consequences
- Positive: the most dangerous capability in the product is a separate, tiny, auditable process with one command and no data; containers cannot reach it at all; the epic's blast radius is provably zero.
- Negative / debt accepted: a second runtime to install and keep patched, documented in `infra/README.md`; loopback-only means remote operation requires an SSH tunnel (correct, and the same constraint applies to the first-boot setup URL); the private key's custody is an operational procedure this ADR does not solve.
- Migration / rollback path: `systemctl stop devon-sentinel` removes the capability with no state loss. Adding `wipe` in EPIC-013 is an allow-list entry plus an executor plus a new ADR — the transport, signing and replay protection are already proven here.

## Alternatives considered
- Wipe inside the application: impossible — the app cannot delete its own container and volumes.
- Unix domain socket instead of a loopback TCP port: genuinely stronger (filesystem permissions instead of an address check) and worth revisiting in EPIC-013; rejected for EPIC-000 because AC-15's disproof is written in terms of binding and addresses (`ss -ltnp`), and matching the criterion's own vocabulary keeps the evidence unambiguous.
- mTLS instead of detached signatures: rejected — certificate lifecycle management for a single loopback caller is more moving parts than ed25519 plus a nonce file.

# ADR-012: Four locales via gate configuration, `t('dotted.key')` over Paraglide, and strengthen-only gate extension

- **Date:** 2026-09-06   **Status:** accepted
- **Deciders:** wp-architect   **Epic:** EPIC-000

## Context
I-9 and decision 6 require `uz-Latn` (default), `uz-Cyrl`, `ru`, `en`, each 100 %. `agentic/gates.json` `limits.locales` names exactly those four ids. `agentic/scripts/check-i18n.mjs` defaults to `['uz','ru','en']` and reads an optional `agentic/i18n.config.json`; it detects used keys **only** as `t('a.b.c')` or `i18nKey="a.b.c"`, and detects hard-coded text only in JSX text nodes. TECH-SPEC §12 states the i18n gate must also cover ru plural completeness. Paraglide 2 compiles messages to `m.some_key()` accessors. `uzbekistan-context.md` §313 establishes that Uzbek takes a singular noun after a numeral, so English/Russian plural logic actively produces wrong Uzbek.

## Decision
Four-way parity is switched on by **adding `agentic/i18n.config.json`**, not by editing a gate script — locales `["uz-Latn","uz-Cyrl","ru","en"]`, messages at `packages/i18n/messages/<locale>.json`, `allow_hardcoded` empty and kept empty (adding an entry is a reviewer finding). `apps/web` calls a thin `t('shell.nav.board')` wrapper exported by `@devon/i18n` that maps dotted keys onto Paraglide's compiled accessors — **because the gate can only see that call shape**, and a gate that cannot see its subject is a gate that passes vacuously. Where `check-i18n.mjs` must grow to meet TECH-SPEC §12 (user-facing JSX attributes `placeholder`/`title`/`aria-label`/`alt`/`label`, and ru plural completeness for ICU plural messages), the change is **strengthen-only**: a meta-test (`packages/i18n/test/gate-strength.test.ts`) asserts the script exits non-zero on each of five synthetic breakages — missing `ru` key, missing `uz-Cyrl` key, hard-coded JSX text, hard-coded `placeholder`, ru plural missing `few` — so a later weakening is itself a test failure. `uz-Cyrl` is produced by a checked-in Latn→Cyrl transliterator, never re-translated; a native reader's sign-off is a separate backlog item. Plural handling: `uz-Latn`/`uz-Cyrl` use `{count} {singular-noun}` with a separate unsuffixed key for bare headings — two keys, never one pluralised string.

## Consequences
- Positive: AC-3 is satisfied without touching a gate script's logic; the gate's own strength is under test; four-way parity is a configuration fact that a future epic cannot quietly regress.
- Negative / debt accepted: the dynamic `t()` wrapper defeats Paraglide's per-message tree-shaking, so all messages for the active locale ship (~10–15 kB gz for the shell's ~150 keys) — measured against the 200 kB `size-limit` budget and accepted, because a legible, gate-visible call shape is worth more than a few kilobytes. Extending a gate script is a sharp tool; the meta-test is the guard rail.
- Migration / rollback path: locales are additive (a fifth locale is a config entry plus a message file). Reverting the wrapper would mean rewriting every call site and blinding the gate — effectively one-way, and deliberately so.

## Alternatives considered
- Calling Paraglide's `m.*` directly: rejected — the i18n gate would report `used=0` and its most useful check would be vacuous.
- Editing `check-i18n.mjs` to default to four locales: rejected — configuration is the intended extension point and leaves the shared script reusable.
- Hand-rolling a 40-line i18n runtime instead of Paraglide: tempting and nearly chosen; rejected to stay on the pinned stack (TECH-SPEC §1.2) and to keep `Intl.PluralRules`-backed Russian plural correctness that we would otherwise have to re-implement.

# ADR-013: Exactly-idempotent demo seed with a data-driven demo chip; gates proven non-vacuous by a mutation harness

- **Date:** 2026-09-06   **Status:** accepted
- **Deciders:** wp-architect   **Epic:** EPIC-000

## Context
AC-1 requires that a second seed run change no row counts and exit 0. AC-2 requires that the seed be refused under `NODE_ENV=production` without an explicit demo flag, and that the demo chip be absent on a non-demo boot — its disproof is "the demo chip rendering on a database seeded without `--demo`/`DEVON_DEMO=1`", which rules out an environment-variable-driven chip. AC-14 requires that no gate pass vacuously and that a deliberate defect of each gate's kind makes exactly that gate fail. H17.1 requires the demo seed to be disabled unless `--demo`.

## Decision
**Idempotence** is exact, not approximate: `app.seed_runs(name primary key, checksum)` records each seed module; a module whose checksum already ran is skipped entirely and the command prints `0 rows written` and exits 0. Within a module, every row uses a deterministic UUIDv5 derived from a fixed namespace and a stable natural key (`demo:user:head.sr`), with `on conflict (id) do nothing`. The whole seed runs under `pg_advisory_lock` so two concurrent invocations cannot interleave. `migrate:verify` seeds twice and asserts per-table counts are identical.

**The demo chip is data**: `app.instance_settings.is_demo` is set to true only by the demo seed, surfaced by `GET /api/v1/instance`, and rendered by the header. An environment variable can never make it appear on a non-demo database, and dropping the demo data removes the chip.

**Guards**: `assertDemoAllowed({ nodeEnv, argv, env })` throws unless the demo flag is present; under `NODE_ENV=production` with the flag it additionally logs a loud warning and writes an audit event. `pnpm --filter @devon/db seed:demo:matrix` prints the whole truth table as AC-2 evidence.

**Gate non-vacuity** has two mechanisms. First, `packages/config/test/workspace-scripts.test.ts` fails if any workspace package lacks `typecheck`/`lint`/`test:unit`/`build`, so `pnpm -r --if-present` can never match zero packages. Second, `tools/gate-mutation/` holds one checked-in patch per blocking gate (type error, lint error, failing unit assertion, missing `ru` key, hard-coded JSX string, oversized chunk, axe violation, department-owned table without `department_id`, route without a declared permission, planted credential string); `pnpm gate:mutation --all` applies each, runs **only** the gate it targets, asserts exit 1, and reverts. It is not itself a gate (it mutates the tree) but its patches are reviewable and its output is AC-14's evidence. CI runs `node agentic/scripts/gate.mjs --profile integration` **verbatim** rather than a hand-listed set, so "CI runs a different set of gates" is impossible by construction.

## Consequences
- Positive: re-seeding is safe by design rather than by care; the chip cannot lie about which database you are looking at; the gates' effectiveness is demonstrated rather than assumed, once per epic and cheaply.
- Negative / debt accepted: demo audit rows survive `seed:reset` because `audit.events` has no delete path — documented in `infra/README.md` rather than worked around. The mutation harness is one more thing to maintain; each patch is a few lines and drifts loudly (it fails to apply) rather than silently.
- Migration / rollback path: `seed:reset --demo` removes only rows in the demo UUID namespace and refuses under `NODE_ENV=production`. Adding demo content in later epics means adding a seed module with its own `seed_runs` name; existing modules are never rewritten.

## Alternatives considered
- Truncate-and-reseed for idempotence: rejected — it cannot touch `audit.events` (I-5a) and it would destroy real data if ever pointed at the wrong database.
- `DEVON_DEMO=1` driving the chip: rejected by AC-2's disproof, and correctly so — the chip must describe the data, not the process.
- Removing `--if-present` from `gates.json`: refused — `gates.json` is hook-protected and gates are never edited by an agent (PROTOCOL §3); script parity achieves the same end from our side of the wall.
