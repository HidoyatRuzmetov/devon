## Business and compatibility boundaries

- The limit is **25 enabled undeleted rules**, not 25 stored rules. Paused copies are valid. A resume-all that would exceed the limit refuses without partially enabling anything.
- Existing triggers remain immutable; Duplicate provides a new trigger. Editing and duplicating keep the rule's current enabled state.
- Sparse legacy actions remain readable so a head can repair them. New action writes and re-enable/resume require complete inputs and active eligible targets. Labels/persons from another department are refused.
- New run cursors are versioned base64url `(timestamp,id)` tuples. Existing ISO-timestamp cursors retain their **strictly before timestamp** behavior for compatibility; old timestamp bookmarks inherently cannot address ties at that timestamp. New clients use tuple cursors.
- Assignment and automation recipient eligibility is checked under locks in the **actual write transaction**. A removal that wins first causes refusal; a write that acquires eligibility first commits before the later removal. There is no promise that a departed person's old cards are erased or that an already committed inbox entry is erased by later removal.
- Card assignee/giver values that are unchanged are not rewritten. Historical cards remain editable after departure. Explicit null assignment/giver patch remains allowed. Card creation still defaults a missing/null giver to its creator, as the existing documented contract requires.
- Automatic actions run from committed outbox intent. Their individual write phases retain existing transaction boundaries; this repair does not assert all-or-nothing atomicity across every action in one rule or external delivery.
