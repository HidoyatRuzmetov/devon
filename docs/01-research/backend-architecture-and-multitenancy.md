# Backend architecture, multi-tenancy for many ministries, on-prem deployment

**TL;DR**: Build on Postgres 17 as the single system of record — it now does relational data, full‑text search (Russian works out of the box, Uzbek does not and needs a custom config), vectors (pgvector), and job queues (pg‑boss) well enough to defer three separate services for the first 1–2 years. Start with shared‑schema + `tenant_id` + Postgres Row‑Level Security (RLS) for multi‑tenancy — it is the only strategy that scales to "many ministries" without a linear ops burden — and hold schema‑per‑tenant in reserve only for a ministry whose legal/security team demands physical separation. Pick TypeScript on Node with Fastify (not NestJS, not Hono) for the API, Drizzle (not Prisma) as the ORM because Drizzle has first‑class RLS support and Prisma's is thin; this also matches the CIS/Uzbek hiring pool far better than Go or Elixir. Ship on Docker Compose for the single-ministry box today and hold Kubernetes/k3s in reserve for when you have more than ~5 tenants or need HA — k3s, not full k8s, because it is a single ~70 MB binary suited to small government server rooms. Treat MinIO, Redis/Valkey, and Meilisearch as swappable commodity sidecars behind clean interfaces, not load-bearing architectural bets, because all three have had real 2024–2025 licensing/scope shocks that a government IT department will not tolerate mid-contract.

## 1. Language/runtime: TypeScript wins on people, not raw performance

| Option | Verdict for this project | Why |
|---|---|---|
| **TypeScript/Node (Fastify)** | **Recommended** | One language across frontend (React) and backend halves the hiring problem and the codebase's cognitive load for a 23-person department growing to a multi-ministry team. Fastify is a thin, fast, plugin-based HTTP framework — no forced architecture, so a first-time backend hire is productive in days. |
| NestJS | Adapt only if the team already knows Angular-style DI | NestJS is Node's most "enterprise" framework: modules, decorators, dependency injection, an out-of-the-box architecture inspired by Angular [nestjs.com]. That structure is valuable at 15+ backend engineers; at 2–4 it is ceremony — more files, more indirection, more onboarding time for a "zero training curve" product. It runs on Express by default (swap to Fastify adapter for speed). |
| Go | Avoid as primary | Excellent performance and single-binary deployment (this is why Centrifugo, k3s, and pg-boss's spiritual peers are written in it), but the Uzbek/CIS junior-to-mid hiring pool is overwhelmingly PHP/Java/1C/.NET/JS, not Go. Using Go would mean either importing expensive specialists or growing them slowly — a risk for a platform whose selling point is being maintainable by an ordinary in-house government IT team. Worth revisiting only for a narrow, high-throughput service (e.g., the realtime gateway or a search indexer) — Centrifugo already gives you that in Go without you writing Go. |
| .NET (C#) | Avoid, but note as the "government-safe" fallback | .NET has real traction in CIS enterprise/government shops (many hire from a large existing pool of "1C"/.NET developers), and Microsoft's ecosystem is culturally familiar to ministries already on Windows Server/AD. But it doesn't share a language with the React frontend, and Uzbekistan's govtech scene skews toward PHP and JS more than C#. | Bun (runtime) | Adapt — pilot for tooling/CI, not the production API | Fast native-TS runtime with a stated goal of 100% Node.js API compatibility and strong coverage of the HTTP/fs/net surface Fastify+Drizzle need, but TLS-corner and process-introspection gaps remain and it lacks Node's decade of production war stories at government-uptime stakes. ## 2. Postgres 17 as the system of record

Postgres 17 (released Sept 2024, now the current stable major as of Sept 2026, with 18 also GA — pin to 17 for a 2026 build and plan the 18 upgrade path) brought concrete wins relevant here: vacuum now uses up to 20x less memory, WAL throughput is up to 2x under high concurrency, `COPY` exports are up to 2x faster, BRIN indexes support parallel builds, and — critically for HA — logical replication slots survive a major-version upgrade and there's a new `pg_createsubscriber` tool to turn a physical replica into a logical one for near-zero-downtime upgrades [postgresql.org/about/news/postgresql-17-released-2936]. `pg_basebackup` now supports incremental backups with a `pg_combinebackup` utility to reconstruct fulls — useful alongside pgBackRest.

**Row-Level Security** is the mechanism that makes shared-schema multi-tenancy safe: policies are evaluated per row, default-deny when no policy exists, and permissive policies OR together while restrictive ones AND together [postgresql.org/docs/current/ddl-rowsecurity.html]. Two real gotchas to design around from day one:
- **Sub-query race condition**: a policy that checks `tenant_id` against a lookup table can, under READ COMMITTED, see stale lookup data concurrently with fresh target-table data, momentarily exposing rows across tenants. The documented fix is `SELECT ... FOR SHARE` in the policy sub-query or wrapping the check in a `SECURITY DEFINER` function — do this from the first migration, not retrofitted later.
- **Metadata leakage via constraints**: unique/foreign-key constraint violations bypass RLS and can leak the *existence* of another tenant's row (e.g., "duplicate key" on an email that belongs to another ministry). Any uniqueness constraint that could cross tenants must be scoped to `(tenant_id, column)`, never global.

**pgvector** (current 0.8.x) supports HNSW and IVFFlat approximate indexes plus exact search across L2/cosine/inner-product/Hamming/Jaccard distances [github.com/pgvector/pgvector] — enough for "find similar projects/comments" or a future AI search feature without standing up a separate vector database. **Partitioning** got easier in 17 (identity columns and exclusion constraints now work on partitioned tables) — plan to partition the audit/event log by month once volume justifies it.

## 3. ORM: Drizzle over Prisma over Kysely

| | Drizzle | Prisma | Kysely |
|---|---|---|---|
| RLS support | First-class: `pgPolicy()`, roles via `pgRole()`, provider helpers for Neon/Supabase [orm.drizzle.team/docs/rls] | No first-class RLS API found in current docs; typically requires raw SQL/`$queryRaw` to set session variables per request | N/A — it's a query builder, not an ORM; you write the SQL yourself so RLS is "just SQL" |
| Philosophy | SQL-like, schema-as-TypeScript, thin runtime | Schema-first DSL (`.prisma` files), generates a client, more "magic" | "Thin abstraction layer over SQL, crafted by SQL lovers for SQL lovers" — zero runtime deps, runs on Node/Deno/Bun/Workers/browser [kysely.dev] |
| Type safety | Strong, inferred from schema | Strong, generated types | Strongest — compile-time errors on non-existent tables/columns |
| Migrations | `drizzle-kit` | Prisma Migrate (mature, widely used) | None built-in; pair with a separate migration tool |
| Team learning curve | Low if team knows SQL | Low to start, friction when you need something the DSL doesn't express (raw RLS, complex partitioning) | Lowest ceiling but requires SQL comfort |

Recommendation: **Drizzle** for the main app (RLS is core to the multi-tenancy strategy, and Drizzle is the only one of the three with a documented, first-class API for it) with **Kysely** as an escape hatch for the handful of gnarly reporting/aggregation queries where even Drizzle's query builder gets awkward. Avoid Prisma for this project specifically because the RLS gap forces raw SQL anyway, at which point Prisma's abstraction is paying for nothing.

## 4. Multi-tenancy strategy: the real decision

| Strategy | Security audit story | Migrations | Noisy neighbours | Data localization | "Our ministry wants its own instance" politics | Ops cost at 10+ tenants |
|---|---|---|---|---|---|---|
| **Shared schema + `tenant_id` + RLS** | Harder to *prove* to an outside auditor at a glance (relies on policies being correct everywhere) but strongest for *continuous* enforcement — DB itself blocks cross-tenant reads even if app code has a bug | One migration run, applies to all tenants at once — fastest, but a bad migration is felt by everyone simultaneously | Real risk: one ministry's heavy report query can starve another's requests unless you use connection pooling limits, statement timeouts, and query cost budgets per tenant | Trivial — one DB, one physical location, one place to prove compliance | Weak answer — "you're on the same server as the Ministry of X" is a hard sell politically even when it's technically fine | Lowest — this is what lets you serve many small ministries economically |
| **Schema-per-tenant** (same DB, `ministry_x.*` schemas) | Easier to explain to an auditor ("your ministry's tables are namespace-isolated") | Must run N migrations (once per schema) — becomes an operational chore past ~20–30 tenants; drift between schemas is a real failure mode | Better isolation than shared-schema for query patterns, still shares the same DB engine/CPU/IO | Same DB instance = same physical location, so still fine for localization | Better story than shared-schema, still "same server" | Medium — fine for 5–30 tenants, painful beyond that |
| **Database-per-tenant** | Cleanest audit story — literally a separate database, separate credentials, separate backup | Full migration tooling must be run per database — needs real orchestration (e.g., a fleet migration runner) | Best isolation short of separate hardware | Fine as long as all DBs sit in the same in-country facility | Good story ("your own database") | High — connection pooling, monitoring, and backup multiply per tenant |
| **Separate deployment per ministry** (own VM/box, own stack) | Best possible audit and sovereignty story — a ministry can literally point at "their" server in their own server room | Each deployment upgraded independently — you now maintain N versions in the wild unless you enforce lockstep upgrades | Total isolation | Trivially satisfies "our data never leaves our building" — often the actual political ask, not a technical one | The winning story politically — "your own instance in your own data center" | Highest — this is what "on-prem software" vendors usually end up doing, and it is exactly why traditional gov software vendors have huge, slow professional-services arms |

**Recommendation for this project**: start **shared-schema + RLS** for the home department and any small/trusted ministries (this is what the product needs to actually be usable, cheap, and centrally improvable — a core promise of "goes viral across government"). Package the **same codebase** so it can be deployed as a **single-tenant instance per ministry** (Docker Compose, one Postgres, `tenant_id` still present internally but always exactly one row) for a ministry whose leadership insists on "our own instance" — this is overwhelmingly a political/trust ask, not a technical one, and you should treat it as a deployment topology choice, not a different architecture. Never build two different codepaths for shared vs. dedicated — same schema, same RLS policies (a single-tenant deployment's RLS policy is just `tenant_id = 'this-ministry'` and mostly inert), same migrations, so you maintain one product, not two.

## 5. Event-driven design, audit trail, and background jobs

An **append-only event log** (`events` table: `id, tenant_id, aggregate_type, aggregate_id, event_type, payload jsonb, actor_id, created_at`) doubles as the audit trail the reference prototype's roadmap explicitly calls for ("log who viewed/changed sensitive data"). Use the **transactional outbox pattern**: write the business-entity change and the outbox event in the same DB transaction, then a relay process publishes it — this guarantees "the message is sent if and only if the transaction commits," avoiding the classic dual-write bug where a DB commit succeeds but the notification/webhook never fires (or fires twice) [microservices.io/patterns/data/transactional-outbox.html]. This is "event sourcing lite," not full event sourcing — you keep normal mutable tables as the fast-read source of truth and use the event log for audit, notifications, and the Friday-update/auto-escalation automation the reference prototype needs, not for reconstructing state by replay (full event sourcing adds real complexity that isn't justified for ~23–100 users).

**Background jobs**: start with **pg-boss** — it runs entirely on Postgres using `SKIP LOCKED` for exactly-once delivery, supports LISTEN/NOTIFY for low-latency pickup, and lets jobs be created inside the same transaction as the business write [github.com/timgit/pg-boss]. This removes an entire infrastructure component (no Redis, no separate broker) for a system at this scale — the auto-escalation queue, weekly-reminder emails, and quarterly profile-verification nudges are all a good fit. Move to **BullMQ** (Redis-backed, mature, used by Slack/Zapier-scale teams, supports retries/rate-limiting/parent-child job flows/cron [docs.bullmq.io]) only if you outgrow pg-boss's throughput or need its richer flow/rate-limit primitives. Reserve **Temporal** for a much later phase, if ever — it is built for genuinely long-running, multi-day, externally-coordinated business processes (e.g., "move money between accounts," "deploy infrastructure") [temporal.io] and would be considerable operational overweight for a department ops tool; do not adopt it just because it's fashionable.

## 6. Search, files, realtime, cache, email

**Search**: Postgres full-text search has Russian built in (`russian` text search configuration with Snowball stemming ships in core) but **no Uzbek configuration exists in core Postgres** [postgresql.org/docs/current/textsearch-dictionaries.html] — you will need to either build a custom Uzbek Snowball-style dictionary/config or accept degraded stemming for Uzbek queries (still usable via `simple` configuration + trigram/`pg_trgm` fuzzy matching as a fallback). This is a real gap to plan for explicitly, not assume away. For a department-scale tool, Postgres FTS + `pg_trgm` is enough through Phase 1–2; only reach for a dedicated engine once cross-entity, ranked, typo-tolerant search becomes a core UX pillar. Between the two candidates: **Typesense** includes Raft clustering with automatic failover in its open-source edition, while **Meilisearch Community Edition** is, for practical HA purposes, effectively single-node — Meilisearch's own pricing page lists "Sharding & Replication: Distribute data across shards and replicas for high availability at scale" as an Enterprise-only benefit, and its public self-hosted documentation describes no multi-node clustering path for the free edition [meilisearch.com/pricing; typesense.org/docs/overview/comparison-with-alternatives.html]. **Correction to an earlier pass**: treat this as strongly corroborated, not airtight — Meilisearch does not publish one explicit "Community Edition is capped at a single node" sentence in its self-hosted docs; the conclusion rests on the *absence* of any documented multi-node feature there combined with sharding/replication being listed as Enterprise-only on the pricing page. Re-confirm directly with Meilisearch (or a support ticket) before this becomes load-bearing for an uptime SLA. For a government system where uptime matters and budget for enterprise search licensing won't exist, **Typesense** is the safer open-source bet if/when you outgrow Postgres FTS; avoid OpenSearch/Elasticsearch until you have real log/observability-scale data, since they demand JVM/Lucene/shard expertise most in-house teams won't have.

**Files**: MinIO is the default S3-compatible choice, but treat it cautiously — MinIO's GitHub repository was archived and, as of 2025, **the community edition no longer ships pre-compiled binaries**: MinIO's own README states it plainly — "The MinIO community edition is now distributed as source code only. We will no longer provide pre-compiled binary releases for the community version" — with legacy binaries frozen and explicitly *not* receiving updates [github.com/minio/minio]. **Correction to an earlier pass of this report**: this is narrower than "costing self-hosters the web console/UI." The embedded web console is **not** gone — the same README confirms "the MinIO Console, an embedded web-based object browser[,] built into MinIO Server" remains present when built from source. Don't conflate this 2025 binary-distribution change with MinIO's separate, earlier (2023) controversy over restricting *console* binaries specifically — different change, different year. The practical consequence for us is a CI/CD line item, not a UI regression: self-hosting now requires a source-build stage (`go install` or a self-built Docker image) to get security fixes and new features, which must be added to the deployment pipeline rather than pulling a prebuilt tag. It remains AGPLv3-licensed and usable, but design the storage layer behind an S3-compatible interface so you can swap providers (Garage, SeaweedFS, or a managed provider) without an application rewrite. Pair with ClamAV for virus scanning on upload and generate previews server-side (PDF/image thumbnails) rather than trusting client-provided previews.

**Realtime**: **Centrifugo** is the right tool — a mature (10-year), Go-based, self-hosted real-time server supporting WebSocket/SSE/HTTP-streaming, horizontally scalable via Redis/Postgres/NATS as the broker, documented to 1M concurrent connections and 30M messages/min on standard hardware, and explicitly designed to bolt onto an existing app with no architecture changes [centrifugal.dev]. This is far less operational burden than hand-rolling a WebSocket gateway, and far more proven than Soketi for a government deployment. OSS is free; Centrifugo PRO adds analytics/tracing/SSO if ever needed.

**Cache**: Redis's licensing changed in March 2024 (effective with Redis 7.4+) to dual **RSALv2/SSPLv1** — no longer OSI-approved open source, with the explicit restriction that you cannot resell Redis as a competing managed service [redis.io/blog/redis-adopts-dual-source-available-licensing]. Internal, non-competitive self-hosted use (exactly our case) remains fully permitted and free, so this is not a blocker — but it is reputational and legal-review friction for a government IT department. **Valkey** (the Linux-Foundation-backed BSD-licensed fork that emerged in response) is the safer long-term default for a government context that wants clean OSS licensing without any ambiguity; it's a drop-in replacement.

**Email**: for a government deployment, prefer routing through an existing **gov SMTP relay** where the ministry already has one (simplest, most compliant, least new infrastructure). Where none exists, **Postal** is a credible self-hosted alternative to SendGrid/Mailgun/Postmark, Ruby-based with Docker support and a full admin UI/API [github.com/postalserver/postal] — but it's another service to patch and secure; only stand it up if no gov SMTP option exists.

## 7. API style, observability, deployment, backups

**API style**: REST + OpenAPI remains the right default for anything that other ministries will integrate with — it is the lowest-common-denominator standard every government IT contractor can consume regardless of their own stack. tRPC is excellent internally (end-to-end TS type safety, zero codegen) if the frontend and backend stay in the same monorepo, but it actively hurts external interoperability, so use tRPC for the internal app's own API and expose a separate versioned REST+OpenAPI surface for cross-ministry integrations, webhooks, and any future "other ministries build against us" ambition. Avoid GraphQL — its query-complexity and caching overhead isn't justified at this data shape (a few dozen well-known entities, not a sprawling graph), and it adds a real learning-curve tax against the "zero training" goal for future in-house maintainers.

**Observability**: OpenTelemetry is the vendor-neutral standard for traces/metrics/logs and works with Grafana/Loki/Tempo/Prometheus or Jaeger as the backend [opentelemetry.io/docs/what-is-opentelemetry]. This Grafana-stack combination is the right self-hosted default: it's fully open source (AGPL/Apache mix, well-understood), lightweight enough for a single-ministry box, and avoids Elastic-stack's JVM overhead. Sentry self-hosted is worth adding specifically for error tracking/alerting (distinct from metrics/traces) once the team is large enough to need triage workflows — note it runs under Sentry's Functional Source License (BSL-style), free for internal self-hosted use but not resellable, which is fine here.

**Deployment**: **Docker Compose** for the initial single-ministry box (Postgres, app, Redis/Valkey, MinIO, Centrifugo — 5–6 containers, one `docker compose up`, entirely manageable by a generalist government sysadmin). Move to **k3s** (not full Kubernetes) once you're serving several ministries from shared infrastructure or need HA — k3s ships as a single binary under 70MB, is a CNCF-certified Kubernetes distribution explicitly designed for "unattended, resource-constrained, remote locations," and supports air-gapped installs via pre-bundled images [k3s.io]. This matches the eventual multi-ministry topology (either one k3s cluster with per-tenant namespaces, or k3s per ministry) without forcing full k8s operational complexity onto a team that doesn't have dedicated SRE staff.

**Backups/PITR**: **pgBackRest** (MIT-licensed) is the standard for this — supports full/differential/incremental (including block-level) backups, parallel compression, delta restore, and multiple repositories for both fast local recovery and redundant remote copies, explicitly built to scale to the largest Postgres workloads without the "time resolution issues" of simpler tools [pgbackrest.org]. Combine with Postgres 17's improved `pg_basebackup` incremental support. Define and rehearse an actual DR runbook (restore-to-point-in-time drill at least quarterly) — a backup nobody has restored is not a backup.

**Feature flags**: OpenFeature is the vendor-neutral standard API (Apache 2.0) with 50+ provider integrations including Unleash, so adopting OpenFeature's client API now and pointing it at a self-hosted Unleash instance later costs nothing and avoids lock-in [openfeature.dev]. For a system this size, don't over-invest early — a simple `feature_flags` table + admin UI can precede a dedicated flag service; migrate to Unleash only once you have real need for percentage rollouts or per-ministry flag targeting.

## What this means for us

1. **[ADOPT] Postgres 17 as the single system of record** — relational + FTS + vectors + job queue in one engine minimizes the services a small in-house team must operate; this is the single highest-leverage decision.
2. **[ADOPT] Shared schema + `tenant_id` + RLS as the default multi-tenancy strategy**, with per-ministry Docker Compose deployment as the "your own instance" escape valve using the *same* codebase and schema — never fork the product for politics.
3. **[ADOPT] TypeScript/Fastify over Go/.NET/Elixir** — matches the local hiring market and lets frontend/backend engineers cross over, which matters more for a small, growing team than raw throughput headroom you won't need for years.
4. **[ADOPT] Drizzle over Prisma** specifically because Drizzle has a documented, first-class RLS API and Prisma does not — RLS is core to the security model, not an add-on.
5. **[AVOID] NestJS as the default** — its Angular-style ceremony is real value at 15+ engineers but active friction against a "zero training curve" product built by a small team; keep it noted as an option if the backend team later grows and wants a more prescriptive structure.
6. **[ADOPT] pg-boss for background jobs before BullMQ/Temporal** — one fewer moving part (no Redis needed for jobs), transactional job creation, sufficient for reminders/escalations/reports at this scale.
7. **[AVOID] Event sourcing (full)** — adopt the outbox-pattern "event sourcing lite" for audit trail and notifications, but keep normal mutable tables as the source of truth; full event sourcing is unjustified complexity here.
8. **[ADAPT] MinIO** — use it, but hide it behind an S3-compatible interface from day one; the 2025 community-edition console/source-only shift is a live warning that this component may need to be swapped.
9. **[ADAPT] Redis license risk → default to Valkey** — internal self-hosted use of Redis remains legally fine, but Valkey removes any future ambiguity for a government legal review and is a drop-in replacement.
10. **[ADOPT] Centrifugo for realtime** — mature, proven at large scale, zero architecture change required; don't hand-roll WebSocket infrastructure.
11. **[ADOPT] Typesense over Meilisearch if/when a dedicated search engine is needed** — Meilisearch Community Edition's single-node-only limitation is a real production risk; Typesense has OSS clustering/failover.
12. **[AVOID] Building a Uzbek stemming solution as a Phase-1 task** — Postgres core has no Uzbek FTS configuration; ship with `simple` config + `pg_trgm` fuzzy match for Uzbek text and flag proper stemming as a Phase 2/3 investment (or an OpenSearch-with-custom-analyzer project) once search becomes a core workflow, not before.
13. **[ADOPT] REST+OpenAPI as the external/cross-ministry contract; tRPC only internally** — the moment "other ministries integrate with us" becomes real, OpenAPI is the only surface every government contractor's stack can consume.
14. **[ADOPT] Docker Compose first, k3s later** — resist Kubernetes until there are enough tenants or an HA requirement to justify it; a government sysadmin without SRE training can run Compose, not a k8s cluster.
15. **[ADOPT] pgBackRest + a rehearsed quarterly PITR restore drill** — the data-localization law makes losing the only in-country copy an existential and legal risk, not just an ops inconvenience.

## Gap-fill addendum

*Added 2026-09-04. Covers items flagged as missing from the original pass: Bun, Hono, API rate limiting, webhooks, tenant provisioning, zero-downtime upgrades, disaster recovery, Flagsmith, secrets management, authentication/authorization, connection pooling, and air-gapped CI/CD.*

### A1. Bun: not adopted now, but worth a v2 pilot

Bun (current: v1.4.x, per its own docs, targeting Node.js v26 API compatibility) states "every day, Bun gets closer to 100% Node.js API compatibility" and that "millions of npm packages intended for Node.js work with Bun" [bun.sh/docs/runtime/nodejs-apis]. Its `node:http`, `node:net`, `node:stream`, and `node:fs` implementations are reported as fully or near-fully implemented, which covers what Fastify and a Postgres driver (`pg` or `postgres`) need at the surface level. The real risk is in the corners that matter for a production API: TLS session resumption across processes and some OCSP-stapling behavior are incomplete (Bun uses BoringSSL, not OpenSSL, which occasionally causes subtle handshake differences), and process-introspection APIs (`getActiveResourcesInfo`, `_getActiveHandles`) return empty arrays — exactly the kind of function a Node.js connection-pool library or a PgBouncer-adjacent health check might quietly depend on for diagnostics. Bun's own ecosystem-compatibility promise is strong but self-reported; it has not been battle-tested at government-uptime stakes the way Node has for a decade.
**[ADAPT]** Do not put Bun under the production API for the initial ministry deployments — Node.js remains the safer choice precisely because "boring and proven" matters more than a faster cold start for a system whose failure mode is a government department losing its work records. Do pilot Bun for two lower-stakes, high-value spots where its strengths are decisive: (1) the CLI/build tooling and test runner (`bun install`, `bun test` are already meaningfully faster than npm/Vitest for CI feedback loops) and (2) a future edge/webhook-relay worker where fast cold start matters and blast radius is small. Revisit full API-runtime adoption at the next architecture review once Bun ships a couple more majors and the ecosystem has more multi-year production war stories.

### A2. Hono: no verdict change, but name the reason for exclusion

Hono is "a small, simple, and ultrafast web framework built on Web Standards," explicitly designed to run unmodified across Cloudflare Workers, Fastly Compute, Deno, Bun, Vercel, Netlify, AWS Lambda, and Node.js [hono.dev]. That multi-runtime portability is Hono's entire reason for existing — it is optimized for teams that don't yet know (or need to keep open) which serverless/edge platform they'll deploy to. This project has the opposite constraint: it is committing to a specific, known deployment target (on-prem/gov-cloud Docker Compose → k3s), where Fastify's larger plugin ecosystem (`@fastify/rate-limit`, `@fastify/multipart`, `@fastify/postgres`, schema validation, swagger generation, etc.) and decade of production hardening matter more than portability to a serverless runtime this project will never target.
**[AVOID]** Hono for the main API. Its value proposition (write once, run on any JS runtime including edge) solves a problem this project does not have. Keep it noted as the right choice *if* a future requirement emerged for a genuinely edge-deployed component (e.g., a lightweight webhook receiver fronting Cloudflare in a hybrid cloud/on-prem topology) — a scenario worth revisiting only if the deployment model changes.

### A3. API-level rate limiting: per-tenant and per-IP, at the edge and in the app

The brief's rate-limiting ask is about protecting the public REST surface (cross-ministry integrations, webhooks-in), which is a different concern from BullMQ's job-level throttling already covered. Two layers, both needed:
- **Reverse-proxy layer**: Caddy/nginx (already in the reference architecture for TLS/subdomain routing) can rate-limit by IP or header cheaply before a request ever reaches the app — the first line of defense against a runaway script or basic DoS, independent of the app being healthy.
- **App layer, per-tenant**: `@fastify/rate-limit` supports per-route configuration, a pluggable key generator (so the limit key can be `tenant_id` extracted from the auth token rather than IP — critical, since many users from one ministry can share a NAT'd IP, and one hostile actor should not be able to lock out an entire ministry by IP-based limiting alone), and a Redis/Valkey-backed store so limits are enforced consistently across multiple app instances rather than per-process [github.com/fastify/fastify-rate-limit]. This maps directly onto the Valkey instance already in the architecture — no new infrastructure.
**[ADOPT]** `@fastify/rate-limit` with a `tenant_id`-based key generator backed by the existing Valkey instance, plus IP-based limiting at the Caddy/nginx layer as defense-in-depth. Set generous default quotas (this is an internal-first tool, not a public API under attack by default) but make per-tenant overrides an admin-configurable value from day one — a ministry that later exposes the REST API to its own downstream integrators will need to raise its own tenant's ceiling without a code deploy.

### A4. Webhooks: adopt the Standard Webhooks spec, self-host Svix or build the same shape

The brief explicitly asks for webhooks and none of delivery, retries, signing, or a management UI existed anywhere in the original report. Two decisions:
- **Wire format**: adopt the **Standard Webhooks** specification — an open, vendor-neutral spec for webhook security and interoperability (HMAC signing, replay-attack and SSRF protection, consistent headers), with a technical steering committee including Svix, Zapier, Twilio, Kong, and Supabase, and reference libraries in eight-plus languages including TypeScript [standardwebhooks.com]. Adopting the spec (rather than inventing a bespoke signature header scheme) means any ministry's own integration team, or any future integrator, can verify signatures using an existing off-the-shelf library instead of reading our custom docs.
- **Delivery infrastructure**: **Svix** is open source (MIT license) and self-hostable — the server is Rust-based, runs against the Postgres we already have plus optionally Redis, and its own docs state it "takes care of deliverability, retries, security, and more," with symmetric (pre-shared key) HMAC by default and asymmetric (ed25519) as an option [github.com/svix/svix-webhooks]. The caveat: Svix's own repo notes some hosted-service features/optimizations "are not yet available in this repo" for self-hosters, and it does not obviously ship a full end-user management UI in the OSS tier — validate this against the current self-hosting docs before committing, and budget for building a thin internal admin screen (list endpoints, view delivery logs, manual redeliver) on top of Svix's API if the OSS UI is too thin.
**[ADOPT]** Standard Webhooks as the signing/payload spec regardless of delivery engine choice — this is nearly free and buys interoperability. **[ADAPT]** Svix self-hosted as the delivery engine — strong odds it removes the need to hand-roll exponential-backoff retry logic and delivery-log storage, but confirm the OSS feature set (especially any admin UI) against current docs before finalizing; the fallback if it's too limited is a `pg-boss`-driven outbound-webhook worker (reusing the existing outbox-relay pattern from §5) with Standard Webhooks signing bolted on — more work, but zero new infrastructure.

### A5. Tenant provisioning and seeding: make it a scripted, idempotent operation from day one

Because the multi-tenancy strategy is shared-schema + RLS with a `tenant_id` on every table, "provisioning a new ministry" is a data operation, not an infrastructure operation — this is one of the concrete payoffs of §4's recommendation. The provisioning workflow should be a single idempotent script/CLI command (callable from an admin UI later) that, inside one transaction: (1) inserts the `tenants` row, (2) seeds the tenant's default roles/permissions and lookup tables (sub-department types, activity categories, etc. — copied from a canonical "template tenant" or a versioned seed-data fixture, not hand-typed per ministry), (3) creates the RLS-scoped admin account and a secure one-time credential/invite link (never emails a plaintext password), and (4) emits an `events` row (`tenant_provisioned`) so the existing audit trail and any onboarding automation (e.g., a welcome Telegram bot message, per the reference prototype's Telegram-first orientation) can react to it via the outbox pattern already in §5. Treat "delete/offboard a tenant" as the mirror operation and design it (soft-delete + data-export bundle) from the same day, not as an afterthought — a ministry that wants to leave, or gets consolidated into another agency (not uncommon in Uzbek government reorganizations), needs a clean exit path.
**[ADOPT]** A single idempotent, transactional `provision-tenant` script driven by a versioned seed-data fixture (not manual SQL), wired into the existing outbox/event-log pattern — this turns "onboard a new ministry" from a bespoke engineering task into a repeatable, auditable, five-minute operation, which is exactly the leverage point for the "goes viral across government" ambition.

### A6. Zero-downtime upgrades: expand/contract migrations plus rolling app deploys

Postgres 17's replication/upgrade mechanics (§2) are necessary but not sufficient — the missing half is the *application-level* discipline of never deploying a schema change and a code change that both assume the new shape in the same instant. The standard technique, sometimes called "parallel change," is: never rename or drop a column/table in one step; instead (1) **expand** — add the new column/table alongside the old one, backfill data, deploy app code that writes to both and reads from whichever is populated; (2) run both shapes in parallel for a transition window while confirming the new path is correct; (3) **contract** — once all instances are running the new code, drop the old column/table [martinfowler.com/articles/evodb.html — describes this as "Parallel Change" / "transition phase," including the pattern of a compatibility view standing in for a renamed table during the transition]. Paired with rolling (not big-bang) app container restarts behind Caddy/k3s — so old and new app versions briefly run side by side against the same database — this is what actually delivers "zero downtime," not just the database side of an upgrade.
**[ADOPT]** Expand/contract as a written migration policy from the first schema change, not introduced later once it's painful to retrofit — every `drizzle-kit` migration that is a rename or a `NOT NULL` addition on an existing column should be split into an expand step (this release) and a contract step (a later release, after confirming zero old-shape reads in logs/telemetry). This is cheap to adopt as a habit early and expensive to bolt on after the team has already shipped a dozen breaking one-step migrations.

### A7. Disaster recovery: set explicit RTO/RPO and a real failover runbook

§7's "rehearse a PITR restore drill" is necessary but doesn't answer the two questions a government auditor or ministry leadership will actually ask: *how much data can we lose* (Recovery Point Objective) and *how long can we be down* (Recovery Time Objective). For a department-ops tool holding project records, org data, and personal data under the localization law, a defensible starting target is **RPO ≤ 15 minutes** (driven by pgBackRest's WAL-archiving cadence, not just nightly fulls) and **RTO ≤ 4 hours** for a single-ministry deployment (time to restore from the most recent backup/replica onto standby hardware and repoint DNS/reverse-proxy) — tighter than that requires a warm standby replica, which is a real cost/complexity step up and should be a deliberate decision, not a default. Because data-localization law keeps all copies inside Uzbekistan, "disaster recovery" here means **cross-facility, in-country replication** (e.g., a physical standby in a second government data center or UzInfocom facility, not a foreign cloud region) — this is a real, answerable architecture question once the hosting facility is chosen (see existing open question on gov-cloud/data-center choice). The failover runbook itself should be a short, literal checklist (who has authority to declare a failover, how DNS/reverse-proxy repointing happens, how to verify data integrity post-failover, how to communicate downtime to ministry users, likely over the same Telegram channel the platform already treats as primary) — written down and rehearsed, not improvised during an actual incident.
**[ADOPT]** Publish explicit RTO ≤ 4h / RPO ≤ 15min targets (or whatever the department and hosting reality actually support) as a named SLA in the platform's own documentation, and write a one-page failover runbook alongside the existing quarterly PITR drill — an untested RTO/RPO number is just a guess, and a government platform's credibility partly rests on being able to answer "what happens if the server room floods" concretely.

### A8. Database connection pooling: PgBouncer, transaction mode, and the RLS interaction

This is the single most load-bearing gap: the whole multi-tenancy design (§4) rests on setting a per-request session variable (`app.tenant_id`) that RLS policies check, and the report never discussed how connections are pooled at scale. **PgBouncer** is the standard lightweight connection pooler for Postgres, with three pooling modes — session, transaction, statement — of increasing aggressiveness [pgbouncer.org/features.html]. The critical gotcha: PgBouncer's own feature matrix marks `SET`/`RESET` compatibility as **"Never" under transaction pooling**, and its docs state that in transaction mode "clients must not use any session-based features, since each transaction ends up in a different connection and thus gets a different session state" [pgbouncer.org/config.html]. A naive `SET app.tenant_id = '...'` per request, combined with transaction-mode pooling (the mode you actually want for a many-small-tenants app, since it reuses connections far more efficiently than session mode), would silently leak the wrong tenant's setting onto the next request that happens to land on the same physical connection — a severe, hard-to-detect cross-tenant data exposure bug.
The established mitigation, used by Supabase, Hasura, and other RLS-on-Postgres platforms, is to set the tenant context with **`SET LOCAL`** (transaction-scoped, not session-scoped) *inside the same transaction* as every query that needs it, rather than plain `SET`. Because `SET LOCAL` automatically reverts at transaction end regardless of which physical connection served it, it is safe under transaction-mode pooling even though plain `SET` is not — PgBouncer's docs don't spell this out as an explicit workaround, but it follows directly from `SET LOCAL`'s Postgres-level transaction-scoping semantics and is well-established community practice; treat it as strongly likely correct but validate with a concurrency load test (many simulated tenants issuing concurrent transactions against a small pooled connection count, asserting zero cross-tenant reads) before relying on it in production.
**[ADOPT]** PgBouncer in **transaction pooling mode**, with every Drizzle/RLS-aware query wrapped so it issues `SET LOCAL app.tenant_id = $1` as the first statement of the same transaction as the actual query (Drizzle's transaction API makes this straightforward to enforce centrally in one request-scoped helper, rather than trusting every call site to remember it). **[AVOID]** Session-mode pooling as the default — it sidesteps the `SET`/`SET LOCAL` question entirely but reintroduces the "many small ministries each holding a long-lived connection" scaling problem PgBouncer exists to solve, defeating the point of pooling for exactly the many-small-tenants shape this project has.

### A9. Authentication/authorization: Keycloak (OIDC) now, national ID integration as a later, verified step

No authentication architecture existed anywhere in the original report — a serious omission for a government platform. **Keycloak** is the right default: it is open source (Apache 2.0), self-hostable, a CNCF project, supports OpenID Connect, OAuth 2.0, and SAML natively, includes LDAP/Active Directory federation (relevant if a ministry already runs Windows Server/AD internally, per §1's .NET-shop observation), and provides single sign-on across multiple applications out of the box [keycloak.org]. Point the Fastify API and the React frontend at Keycloak via standard OIDC (authorization-code + PKCE flow) rather than hand-rolling session/password auth — this both removes a large, security-sensitive surface from the in-house codebase and gives every future ministry a known onboarding pattern ("connect your Keycloak realm" or "we provision you a realm") rather than a bespoke integration each time.
Uzbekistan is understood to operate a national digital-identity layer in this space (commonly referenced in-country as "ONE ID," used for e-KYC in banking and some e-government logins), but this pass could not confirm from public documentation whether it exposes a standard OIDC/OAuth2 endpoint suitable for a department-level platform to integrate against — the obvious candidate domains did not resolve during this research pass. This is flagged as an open question requiring a direct conversation with UzInfocom or the ministry's own IT/security leadership, not assumed either way.
**[ADOPT]** Keycloak (self-hosted, OIDC) as the identity provider for the platform itself from day one — realm-per-ministry or a shared realm with per-tenant groups maps cleanly onto the shared-schema+RLS strategy (a Keycloak group/claim maps to `tenant_id`). **[ADAPT]** Design the OIDC integration so a national identity provider (ONE ID or equivalent) can be added later as a Keycloak **identity broker/upstream IdP** rather than a from-scratch integration — Keycloak natively supports federating to an upstream OIDC provider, so if/when the national system exposes a compatible endpoint, connecting it becomes configuration, not a rewrite. **[AVOID]** Building custom password-based auth or a bespoke SSO protocol — both are unnecessary security liability given Keycloak's maturity and free licensing.

### A10. Config and secrets management for air-gapped/on-prem deployment

No proposal existed for how database credentials, SMTP credentials, or API keys are stored, distributed, or rotated — a gap that matters more, not less, in an air-gapped government deployment where cloud KMS/Vault-as-a-service isn't reachable. **SOPS** (Secrets OPerationS, a CNCF sandbox project) encrypts values inside otherwise-plaintext config files (so structure/diffs stay reviewable in git while secret values stay encrypted) and supports fully offline encryption backends — **age** or PGP/GnuPG — alongside optional cloud KMS backends for sites that do have connectivity [getsops.io]. This is the right fit for a small in-house team: secrets live encrypted in the same git repo as everything else, decrypted only at deploy time using a key held by the deploying sysadmin, with zero dependency on reaching an external service — exactly the air-gapped-compatible property Vault's server-based model doesn't give you without its own additional infrastructure and unseal-key ceremony. **HashiCorp Vault** remains worth holding in reserve for a later phase if the platform grows enough tenants/secrets to need dynamic secret leasing, automatic rotation, or a central audit log of who accessed which secret and when — real capabilities SOPS doesn't provide — but that is meaningfully more operational surface (a server to run, unseal, and back up) than a 23-person department needs on day one.
**[ADOPT]** SOPS with the `age` backend for all environment/config secrets, committed encrypted alongside the Docker Compose / k3s manifests in version control — simple, offline-capable, auditable via normal git history. **[ADAPT]** Revisit HashiCorp Vault (or OpenBAO, its open-source fork, which SOPS also supports as a backend) once the platform serves enough ministries that manual key rotation via SOPS becomes an operational bottleneck, not before.

### A11. CI/CD and update delivery for air-gapped/on-prem sites

Nothing in the original report addressed how a new release physically reaches an offline ministry server — a real blocker for "goes viral across government" if every rollout requires someone to hand-carry a USB drive. **Zarf** is a purpose-built, open-source (Linux Foundation project, via Defense Unicorns) tool for exactly this: it packages an application plus all its dependencies into a single deployable bundle, generates a Software Bill of Materials automatically, and stands up offline container-registry and git-server mirrors inside the disconnected environment so deployment there looks like a normal two-command install rather than a bespoke offline procedure [zarf.dev]. It targets Kubernetes-shaped deployments most directly, which aligns with this project's own "Docker Compose now, k3s later" trajectory (§7) — Zarf becomes directly applicable once k3s is in play, and for the earlier Compose-only phase, a simpler equivalent (a signed release tarball containing pinned image digests, pushed to a USB/local-network offline registry mirror, verified via checksum/GPG signature before `docker compose pull`) covers the same need with less new tooling. Either way, the release artifact should always be **cryptographically signed** so an air-gapped sysadmin can verify authenticity without a live connection to a package registry — this is a hard requirement, not a nice-to-have, once the platform is running inside a ministry's own network boundary.
**[ADOPT]** A signed-bundle release process from the first on-prem deployment: pin image digests (not just tags), sign the release manifest, and document a simple offline-verify-and-apply procedure a generalist government sysadmin can follow. **[ADAPT]** Zarf specifically once the platform moves to k3s (§7) — it directly solves the offline registry/GitOps problem that phase introduces; treat it as premature infrastructure while still on single-ministry Docker Compose.

### A12. Feature flags: add Flagsmith to the comparison

The brief named Flagsmith specifically and it was absent from §7's flag-tooling discussion. Flagsmith is open source and self-hostable, with first-class **OpenFeature** integration already documented [docs.flagsmith.com] — meaning it is not actually a competing choice to the OpenFeature-first strategy already recommended in §7, but an alternative *provider* behind that same standard API, same as Unleash. Its differentiator versus Unleash is a friendlier out-of-the-box UI and a slightly more product-led (vs. infra-led) positioning; both are credible self-hosted OpenFeature providers.
**[ADAPT]** Keep the existing §7 recommendation (OpenFeature client API now, a `feature_flags` table + admin UI as the Phase 1 provider) unchanged, but note Flagsmith alongside Unleash as an equally valid future OpenFeature provider — evaluate both once percentage-rollout/per-ministry targeting is actually needed, rather than defaulting to Unleash by inertia.

- **Flagsmith** — named in the brief's feature-flag list but never mentioned; only OpenFeature/Unleash are discussed.
- **Config management / secrets** — no discussion of how environment configuration or secrets (DB credentials, SMTP credentials, API keys) are managed and rotated, which matters a great deal for an air-gapped, multi-ministry, on-prem deployment.

### 2. Adjacent topics a senior product/engineering lead would expect but that are absent

- **Authentication/authorization architecture** — no mention of SSO, OIDC/OAuth, or integration with any Uzbek government identity system (e.g., a national e-ID/single-sign-on equivalent), which is normally one of the first architectural questions for a gov platform and directly shapes the API/session design discussed elsewhere in the report.
- **Database connection pooling (PgBouncer/pgbouncer-rr or built-in pooling)** — critical and conspicuously missing: RLS-per-request plus many small ministries each opening connections is exactly the scenario connection pooling exists for, yet the report's Postgres and multi-tenancy sections never raise it.
- **Secrets management for air-gapped ops** (Vault, SOPS+age, or simpler) — the report's own open questions flag air-gapped licensing risk but never proposes how secrets get distributed/rotated without external services.
- **CI/CD and update-delivery pipeline for on-prem/air-gapped sites** — the report describes Docker Compose/k3s as the runtime target but never addresses how new releases physically reach an offline ministry server (signed update bundles, offline package mirrors, etc.), which is a real-world blocker for "goes viral across government."

### 4. Net assessment

The report's core recommendations (Postgres 17 as system of record, shared-schema+RLS with per-ministry Compose as the politics escape valve, TypeScript/Fastify/Drizzle, pg-boss before BullMQ/Temporal, Centrifugo, Valkey-over-Redis-license-risk) are well-reasoned and mostly well-sourced, and the one material factual issue found (the MinIO console framing) is a nuance correction, not a reversal of the underlying recommendation to abstract MinIO behind an S3-compatible interface. The larger issue is coverage: several items the brief explicitly asked for (Bun, rate limiting, webhooks, tenant provisioning/seeding, zero-downtime upgrades, Flagsmith) were skipped rather than addressed and rejected, and authentication/authorization architecture — arguably the single most important missing topic for a government platform — was never raised at all.
