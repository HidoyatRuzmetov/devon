# Documents, meeting notes, approvals, e-signature, official correspondence

**TL;DR**
1. Notion-style wikis (Notion, Outline, Slite, GitBook) win on adoption because editing feels like typing, not filing; Confluence wins on governance (spaces/permissions/macros) but is widely reported as slow, sprawling, and search-poor at scale — copy the former's UX, not the latter's information architecture.
2. Government document culture in Uzbekistan/CIS is not "wiki + Kanban" — it is number-stamped correspondence (incoming/outgoing registration), orders (приказ/buyruq) with named executors and hard deadlines, and protocols of meetings that spawn tracked assignments; any tool that ignores this pattern will be rejected as "not a real document system" no matter how pretty it is.
3. E-Imzo (run by the State Tax Committee's "Yangi Texnologiyalar" center) is Uzbekistan's legally binding PKI signature and is already the default for citizen/business e-government (my.gov.uz); build to consume E-Imzo tokens (PKCS#7/CAPICOM-style) rather than adopting DocuSign/Documenso as the signature of record — those remain useful only for informal/low-stakes internal sign-off or cross-border documents.
4. Approval UX that actually gets used is one-tap from a chat notification (Lark Approval's model) or one click from an email/Telegram digest — never "log into a portal to approve," which is the single most common failure mode of enterprise BPM rollouts.
5. Build a small, explicit state-machine workflow engine natively (request → approve/reject → execute → report → close, with SLA timers and auto-escalation) rather than adopting Camunda/Temporal/n8n wholesale; reserve a heavier engine only if/when workflow complexity outgrows a hand-rolled model, and use E-Imzo + a document register as the two must-have integrations from day one.

## 1. Knowledge bases / wikis

|---|---|---|---|---|
| **Confluence** | Spaces → pages → macros | SaaS or Data Center (self-managed); commercial | Deep permissions, page history, Jira linkage, mature macro ecosystem | Widely reported as slow to load, "page sprawl" with no reliable way to find the current version of anything, search that surfaces outdated pages above current ones, and a WYSIWYG editor many teams find clunky compared to markdown-first tools. Data Center self-hosting is expensive and heavy for a 23-person department. |
| **Notion** | Flexible blocks/databases, one workspace | SaaS (no self-host); per-seat pricing | Fastest to start writing in, doubles as light project tracker, AI search ("get answers with citations") now central to its pitch, generous free tier for small teams | No robust self-hosting (a blocker for a data-localization requirement covering personal data); permission model is looser than Confluence, so large orgs report "workspace becomes a junk drawer" without discipline. |
| **Outline** | Wiki with collections/documents | **Source-available (Business Source License 1.1), not OSI open source**, public repo (~40k GitHub stars), self-hostable via Docker for internal non-competing use; converts to Apache 2.0 on 1 Sept 2030 (or 4 years from a given version's release, whichever is sooner) | Markdown-native, "blazing fast," real-time multiplayer editing, Slack search integration, dark mode, granular read/write permissions, 20-language i18n including RTL | Smaller plugin/integration ecosystem than Confluence; AI features newer and less proven; BSL forbids reselling Outline itself as a hosted multi-tenant "Document Service" to third parties — irrelevant for our internal self-hosted use, but worth knowing before any resale/reference-implementation reuse. |
| **Slite** | AI-maintained knowledge base | SaaS; commercial | "Self-maintaining" pitch — detects knowledge drift against Slack/Linear/GitHub and proposes updates with human-in-the-loop approval; migration tools from Notion/Confluence | Niche, smaller ecosystem (~1,700 companies cited); less proven at very large scale. |
| **GitBook** | Docs-as-code, Git-sync | SaaS, free tier + enterprise; not self-hostable in the OSS sense | Git branch/PR-style review for content changes, "Agent" flags stale docs, SOC2/ISO27001/SAML available | Built for product/API docs more than an internal operational wiki; heavier lift for non-technical staff to use Git-sync mode. |
| **XWiki** | Structured wiki with apps/macros | **Open source (LGPL)**, self-hostable, Java-based | Full self-hosted control, scriptable "wiki applications," long enterprise/government track record in the EU | Dated UI compared to Notion-class tools; steeper admin learning curve; smaller mindshare in CIS/Central Asia. |

**Contrarian evidence:** the recurring complaint across enterprise wiki tools (Confluence especially) is not "not powerful enough" but **findability** — teams end up with dozens of near-duplicate outdated pages and no page ever feels "the current truth." The fix is structural, not a feature: every document needs an explicit **owner, status (draft/current/archived), and last-verified date**, and stale documents should surface for re-verification rather than silently rot. Notion's newer "AI search with citations" is itself an admission that free-text wikis without curation don't scale past a certain size.

## 2. Meeting notes with action items

| Tool | Approach | Notes |
|---|---|---|
| **Granola** | Local audio capture, **no bot joins the call** — transcribes system audio in the background, calendar-aware pre-briefs, generates action items/follow-up emails after | Praised specifically because it doesn't add an awkward "recording bot" participant — a real concern in government meetings where a visible AI notetaker can itself be a political/security problem. Notes are private-by-default, shareable on demand. |
| **Fellow** | Structured meeting agendas + notes tied to calendar invites, action-item tracking across meetings, 1:1 templates | Strong for recurring meeting cadences (weekly team syncs, 1:1s) — good conceptual fit for the "Friday project comment ritual" already in the reference prototype. |
| **Otter.ai** | Bot joins call, live transcription + summary | Requires a bot in the meeting (same objection as above for sensitive government discussions); strongest for large all-hands/webinar transcription. |
| **Notion (AI meeting notes)** | Notion now bundles meeting-notes capture directly into the same workspace as docs/projects | Reduces tool-switching, but as a bundled feature it is less mature than dedicated tools. |

**Design implication:** for a government department, a locally-hosted or audio-capture-without-a-visible-bot approach is culturally and politically safer than a bot-in-the-call model — and it maps cleanly onto the existing "protocol of meeting" tradition (see §5): every meeting note should be structurally the same object as a **protocol** — attendees, agenda items, decisions, and assignments (who/what/by-when) that flow straight into the workflow engine as tracked instructions.

## 3. Decision records

The Architecture Decision Record (ADR) pattern (Michael Nygard, 2011; formalized via adr.github.io) captures **one decision per short document**: context → decision → consequences, numbered and immutable once accepted (superseded, not edited). It maps directly onto a government "resolution/protocol decision" need: a durable, timestamped, attributable record of *why* something was decided, separate from the correspondence that executes it. Tooling in this space (adr-tools, log4brains, MADR templates) is developer-oriented and lightweight — essentially a markdown template plus a numbered index — which is exactly the right amount of process for a 23-person unit; do not adopt a heavyweight "decision register" product for this.

## 4. Templates, version history, diff, comments/mentions

- **Version history as a first-class, visible feature** (not buried in a menu) is what separates tools people trust with important documents from ones they don't. Confluence and Notion both keep full page history; Outline and GitBook (Git-sync) make diffing explicit — GitBook's pitch that docs are "branched, reviewed, and merged like a PR" is a genuinely good mental model for *official* documents (orders, regulations) where a change needs a visible before/after and an approver.
- **Comments/mentions**: inline, anchored to a text selection (not just page-bottom), with @mention triggering a notification, is now table stakes (Notion, Outline, Confluence, GitBook all do this). The failure mode to avoid is Confluence-style comment threads that get orphaned when the underlying content is edited around them.
- **Templates**: every wiki tool above supports a template gallery; the government-specific value is in **pre-built templates for the actual documents this department produces** — memo (служебная записка), official outgoing letter, meeting protocol, order/instruction (приказ/buyruq), report (отчёт), business-trip order (командировка/xizmat safari). These should be native to our system, not something staff build from scratch in a generic doc tool.

The lesson: ship 4–6 hardcoded workflow *types* (letter approval, order/instruction, leave/business-trip request, purchase/expense, document publication) rather than a generic "build your own BPMN process" canvas.

## 6. E-signature and Uzbekistan's E-Imzo

- **Documenso**: fully open-source (GitHub), self-hostable, positions itself as the DocuSign alternative with API access, templates, and white-labeling; the openness is explicitly valued by its own users ("I can directly read the code"). Good fit for **internal, non-legally-binding sign-off** (e.g., acknowledging a memo) if we want a self-hosted, EU-style e-sign UX without external SaaS dependency.
- **DocuSign**: market leader, tiered at roughly $10 (Personal) / $25 (Standard) / $40 (Business Pro) per user/month, 900–1,000+ integrations; no public-sector-specific plan surfaced on its consumer pricing page — enterprise/government contracts are handled off-list. Legally, a foreign commercial e-signature vendor is very unlikely to satisfy Uzbek requirements for documents that must carry legal force domestically.
- **E-Imzo** (e-imzo.uz → e-imzo.soliq.uz): Uzbekistan's actual legally-binding PKI digital signature, administered by the State Tax Committee's "Yangi Texnologiyalar" (New Technologies) Scientific-Information Center. Citizens/officials obtain a key via an app-based flow (QR code + Face-ID verification in the "Soliq" mobile app, or in person at a State Services Center), and hold private keys as PIN-protected `.pfx` containers, verified through a browser plugin/module. It underlies `my.gov.uz`, the unified e-government portal, and is the default signature for interactions with government systems.
- **Implication**: E-Imzo is not optional infrastructure to "integrate later" — it is the actual legal signature for any *official* outgoing letter, order, or protocol our platform produces. DocuSign/Documenso-style e-signature should be scoped only to informal internal acknowledgments (e.g., "I've read this policy") where legal force doesn't matter; anything that leaves the department as an official document needs an E-Imzo-compatible signing step (PKCS#7 detached signature workflow), likely via a browser widget or the government's existing E-Imzo SDK/API rather than building PKI from scratch.

## 7. CIS correspondence/registry systems and "execution control"

Government and large-enterprise document management in Russia/CIS is dominated by a specific, well-understood pattern that Western tools (Notion, Confluence, Asana) simply don't model:

- **Directum, ELMA365, 1C:Document Management, Docsvision, Bitrix24** are the reference systems. Docsvision alone claims 700,000+ users and penetration in 32% of Russian federal ministries/agencies (per its own marketing, treat as a vendor claim); ELMA365 markets itself as "the most implemented BPM system in the CIS" with 4,000+ clients across enterprise/government/finance, offered SaaS or on-premise. Bitrix24 is the ubiquitous CIS/Central Asian all-in-one (CRM + docs + workflow automation + "requests, approvals, expense reports"), with a generous free tier that likely explains its household-name status in the region.
- **The universal pattern across all of them** — and the one explicitly named in this dimension's brief — is:
  1. **Registration**: every incoming/outgoing document gets a sequential **registration number** (входящий/исходящий №) stamped with date, correspondent, and subject — this number is the document's permanent identity, referenced in all follow-up correspondence.
  2. **Instruction (резолюция/topshiriq)**: a director or head annotates a document with an instruction — free text plus a named **executor** and a **deadline**.
  3. **Execution control (контроль исполнения/ijro nazorati)**: the system tracks open instructions against their deadlines, flags overdue items, and requires the executor to submit a **report** before the instruction can be marked closed.
  4. **Closure**: closing requires either the original assigner's sign-off or an automatic rule (e.g., report accepted).
- **Meeting protocols** feed this same mechanism: a protocol of a meeting is itself a registered document, and each numbered decision item in it becomes an instruction with an executor and deadline, tracked exactly like a resolution on an incoming letter.
- Uzbekistan's own government tooling (`ijro.gov.uz`, part of the broader e-government stack alongside `my.gov.uz`) is built around this same "instruction → executor → deadline → report" idea at a national level — literally "ijro" means "execution" in Uzbek — confirming that execution-control is not a CIS peculiarity to route around but the **actual mental model** civil servants already have for what a "task" is.

**Design implication — this is the single most important native feature to build**, more important than any wiki or chat feature: a document (or a protocol line-item) must be able to carry one or more **instructions**, each with executor, deadline, and required report, visible in a department-wide "control list" (list of everything overdue or coming due), exactly mirroring what our reference prototype already sketched with weekly project comments and auto-escalation — this dimension should extend that same primitive to documents/orders/protocols, not invent a parallel concept.

## 8. Form builders and file management

- **Tally**: free, unlimited forms/submissions, Notion-like block editor, conditional logic, e-signature/payment fields, 50+ languages, EU-hosted — a strong default for internal request forms (leave request, IT ticket, room booking) given its zero-cost ceiling and low learning curve.
- **Fillout**: comparable no-code builder with "smart routing," 100,000+ organizations claimed, strong integrations; roughly interchangeable with Tally for this use case, decide on integration fit rather than features.
- **Typeform/Formbricks**: Typeform is the premium, more design-forward incumbent (paywalled advanced logic); Formbricks is open-source and self-hostable, relevant if data-localization concerns rule out any SaaS form host entirely — worth a closer look given our hosting constraints, though we could not fetch its site during this research pass.
- **Recommendation**: don't build a form builder natively for v1 — every internal "request" (leave, procurement, IT support, room booking) is a structured object better served by our own workflow engine's typed request forms; reserve an external, embeddable form tool (self-hosted if possible) only for ad hoc one-off data collection (an all-staff survey, an event RSVP list) that doesn't need a workflow behind it.
- **File management / Office editing**: **OnlyOffice** is the standout fit — AGPLv3 open-source, self-hostable (Community/Docspace), edits Word/Excel/PowerPoint-equivalent formats plus PDF forms and Markdown, has native Telegram integration, character/paragraph-level co-editing, and 40+ connectors (Nextcloud, Moodle, etc.) for embedding editors into another app. Collabora Online (LibreOffice-based, also self-hostable, AGPL core) is the other credible open option; OnlyOffice's UI is closer to the familiar Microsoft Office ribbon, which matters for zero-training adoption among civil servants used to Word/Excel. Either should be **embedded**, not replaced with a custom editor — building a rich-text/spreadsheet editor from scratch is not a good use of effort here.
- **Folders vs. tags**: the correspondence/execution-control pattern above implies documents need **both** — a folder-like registry (by year, by correspondent, by sub-department) for the official record, and free tags/labels (by project, by topic) for cross-cutting retrieval; neither alone satisfies both a registrar's need for order and a knowledge worker's need for a topic view.

## 9. Minimal workflow engine design (recommended to build natively)

A small, explicit state machine — not a general BPMN engine — covering the shapes of work this department actually has:

**Core object: `WorkItem`** (covers: outgoing letter approval, order/instruction, meeting-protocol assignment, leave/business-trip request, purchase request, document publication)
```
states:  DRAFT → SUBMITTED → IN_REVIEW → APPROVED|REJECTED → IN_EXECUTION → REPORTED → CLOSED
         (REJECTED can loop back to DRAFT; IN_EXECUTION can branch to ESCALATED on SLA breach)
fields:  type, registration_number (auto, sequential per type/year), title, body/attachment(s),
         requester, approver_chain (ordered list, supports parallel-any / serial-all),
         executor(s), deadline, sla_hours_per_state, escalation_target,
         signature (none | internal_ack | e_imzo), history[] (append-only audit log)
```
- **Steps**: each state transition is a discrete step with an actor, a timestamp, and an optional comment/attachment — this *is* the audit trail, and it is also the "version history" for approvals (who changed what, when).
- **SLAs & escalation**: every state that has an owner (IN_REVIEW → approver, IN_EXECUTION → executor) carries a deadline; a background job checks overdue items on a schedule and (a) notifies the owner, (b) after a grace period, auto-escalates to the owner's manager and flags the item in a department-wide "overdue" list — directly reusing the reference prototype's proven "auto-escalation into management review queue" idea from the Projects module.
- **Notifications**: every state transition fires a notification via **Telegram bot** (primary, given Telegram's dominance in Uzbekistan) and in-app; the approval notification itself should carry inline Approve/Reject buttons (Telegram supports inline keyboards) so approving is literally one tap from the notification — this is the concrete way to hit the "Lark Approval" bar without adopting Lark.
- **Signature step**: optional, pluggable — `internal_ack` (simple in-app confirmation, fine for informal sign-off) or `e_imzo` (redirect to/embed the E-Imzo signing flow, store the resulting PKCS#7 signature blob and its verification result against the document hash) for anything that must be legally binding.
- **Build vs. integrate**:
  - **Build natively**: the WorkItem state machine, registration numbering, SLA/escalation, Telegram notifications, the 4–6 government document templates, the "overdue instructions" dashboard.
  - **Integrate**: E-Imzo for legal signatures (must integrate, cannot build), OnlyOffice/Collabora for in-line Office document editing (must integrate, should not build), optionally n8n as a glue layer for cross-system notifications once integrations multiply beyond what's worth hardcoding.
  - **Avoid**: adopting a full BPM/case-management product (Camunda, ProcessMaker, Kissflow, ELMA365, Directum) as the core of the platform — each one either re-imports a generic, over-flexible mental model that fights "zero training," or (for the CIS ECM products) is a large, commercially-licensed, CIS-vendor-locked system that works against building something unique and ours.

## What this means for us

1. **[ADOPT]** Model every document/protocol item with the CIS "instruction → executor → deadline → report → closure" pattern as the core primitive — it's the one thing every comparable system in this region gets right and every Western tool (Notion, Confluence, Asana) misses entirely.
2. **[ADOPT]** Sequential registration numbers for incoming/outgoing correspondence and orders, stamped automatically — civil servants will not trust a system that can't answer "what is this document's number," a basic administrative reflex in this bureaucratic culture.
3. **[ADOPT]** E-Imzo integration as the signature of record for anything official; do not present DocuSign/Documenso as "the" e-signature — they're fine for informal internal acknowledgment only.
4. **[ADOPT]** One-tap approvals via Telegram inline buttons, mirroring Lark Approval's chat-card UX — this is the highest-leverage single interaction to get right, since approvals are the most frequent action any manager takes.
5. **[ADOPT]** Native government document templates (memo, official letter, protocol, order/instruction, report, business-trip order) rather than a generic blank-page editor — templates encode institutional knowledge and remove the "how do I even format this" barrier for a first-time user.
6. **[ADAPT]** Build a small hand-rolled workflow state machine (states/SLA/escalation) inspired by Temporal's durable-execution vocabulary and Camunda's "human task as first-class" idea, but skip both actual products — reserve real BPM engines for a much later, much larger cross-ministry phase, if ever.
7. **[ADAPT]** Take Confluence/Notion/Outline's editing UX (markdown-first, slash commands, inline comments/@mentions, visible version history) for the wiki/knowledge-base layer, but self-host on something like Outline (**source-available under BSL 1.1, not OSI open source** — self-hosting for our own internal, non-competing use is fine, but the label matters for procurement/legal review — i18n-ready with RTL/Uzbek support) rather than SaaS Notion, given the data-localization law.
8. **[ADAPT]** Borrow GitBook's "changes are reviewed like a PR" mental model specifically for *regulations/policies/orders* that need visible diff + approval before publishing — don't apply it to casual notes.
9. **[ADAPT]** Use Granola-style "no visible bot" audio capture for meeting notes if/when AI transcription is added — a visible AI bot joining a government meeting (Otter-style) is a bigger trust problem here than in a typical Western company.
10. **[ADAPT]** Use ADR-style single-decision, numbered, immutable records for department-level decisions (not just engineering) — cheap, markdown-based, and fits the existing "protocol of decisions" habit.
11. **[AVOID]** Adopting a full CIS ECM suite (Directum, ELMA365, 1C:Document Management, Docsvision) as the platform's foundation — commercially licensed, vendor-locked, generic UI, and directly contradicts the "unique to us" ambition; treat them only as reference points for the *data model* (registration numbers, resolutions, execution control), never as products to license.
12. **[AVOID]** A generic no-code BPM canvas (Kissflow/ProcessMaker/Pipefy-style "build your own process") as the primary approval mechanism — every case study of these tools shows process sprawl and single-power-user dependency, exactly what "zero training" is meant to prevent. Ship a fixed menu of workflow *types* instead.
13. **[AVOID]** Treating Confluence as an aspirational model — its own user base's most common complaint is that it becomes an unnavigable archive of stale pages; if we build a wiki layer, pair every page with an explicit owner + status + last-verified date from day one, or it will rot the same way.
14. **[ADOPT]** Embed OnlyOffice (AGPL, self-hostable, Telegram-integrated, ribbon-familiar UI) for in-browser editing of Word/Excel/PDF-style attachments rather than building or buying a separate document viewer/editor.
15. **[ADAPT]** Use a lightweight external form tool (Tally or a self-hosted Formbricks) only for ad hoc, workflow-free data collection (surveys, RSVPs); route every recurring internal request (leave, procurement, IT) through the native WorkItem engine instead, since those need SLA/escalation/registration, which a form tool alone cannot provide.

### A. File previews (quick-view/thumbnails)

The brief names "previews" explicitly; the base report never addresses it. For a registry where staff triage dozens of incoming letters a day, requiring "open the file to see what it is" is a real tax.

- **Pattern to copy**: Google Drive/SharePoint's model — a thumbnail grid in list views (first-page raster for PDFs/Office docs, native preview for images), a hover/click quick-look panel that opens an inline viewer without leaving the list, and a full inline editor only on explicit "open." Nextcloud Files and macOS Quick Look are the same pattern outside the SaaS world — the idea is old and proven, not novel.
- **Concrete build**: generate a first-page thumbnail (raster PNG, ~300x400) on upload via a PDF rasterizer (pdftoppm/Poppler or pdf.js's canvas renderer) for PDFs, and via OnlyOffice's/Collabora's headless conversion service for Office formats (`docx→pdf→thumbnail`); cache the thumbnail alongside the document blob. For the inline quick-view itself, **PDF.js** (Mozilla, Apache 2.0, embeddable `<iframe>`/canvas viewer, no server round-trip needed once the PDF is fetched) is the right default for read-only preview — reserve the full OnlyOffice editor iframe for when someone actually needs to edit or annotate.
- **[ADOPT]** Thumbnail grid + PDF.js quick-view as a native, always-on feature of the document/correspondence list — this is cheap to build (an existing, mature open-source renderer) and directly serves the "triage dozens of letters a day" reality, not a nice-to-have.

### B. PDF handling as its own topic (annotation, PDF/A archival, OCR)

The base report only mentioned PDF as a line in OnlyOffice's feature list. A direct read of OnlyOffice's PDF editor page confirms it deserves its own subsection because incoming government correspondence *is* PDF (scanned) far more than it is native Office format:

- **Annotation/markup**: OnlyOffice's PDF editor supports highlight, underline, strikethrough, freehand drawing, stamps, and inline comments directly on a PDF — i.e., a reviewer can mark up a scanned incoming letter without converting it to anything else. This is the natural home for the "director annotates with a резолюция/topshiriq" step in §7's execution-control pattern: the instruction can be a stamp/comment anchored to the actual scanned page, not just a separate metadata field.
- **PDF/A archival**: OnlyOffice can save any document (Word, Sheet, Slide, or PDF) as **PDF/A**, the ISO-standardized archival PDF profile (embeds fonts, forbids external dependencies, guarantees long-term renderability). This directly answers the base report's own Open Question about long-term archival — outgoing official letters/orders should be archived as PDF/A at the point of `CLOSED` state in the WorkItem lifecycle, not left as ordinary PDF or (worse) only as the editable source file.
- **Redaction**: OnlyOffice also ships a dedicated redact tool (search-and-blackout by term or page range) — relevant given documents will carry a sensitivity classification (see §E below); redaction is how a `restricted` document gets safely shared at a lower tier.
- **OCR add-on**: OnlyOffice's newer AI helper can extract text from a scanned PDF page directly in the editor ("forget manual retyping, just scan and go") — useful for a single document a person is looking at, but this is a manual, per-document action, not a batch pipeline; it does not substitute for system-wide OCR at ingest (§C).
- **[ADOPT]** Treat PDF/A export as a mandatory step when a WorkItem reaches `CLOSED`/published state, not an optional format choice — this is the cheapest possible fix to the archival Open Question and requires no new tooling since OnlyOffice already does it.
- **[ADOPT]** Use OnlyOffice's native annotation/stamp tools for the resolution/instruction step on scanned incoming letters, rather than building a separate "add instruction" form disconnected from the document image.

### C. OCR / full-text search over scanned incoming correspondence

This was absent entirely from the base report despite scanned paper being the norm for incoming correspondence in this bureaucratic culture — a real gap, since without it the "registration number is the document's identity" pattern (§7) only gives you metadata search, not content search.

- **Paperless-ngx** (verified via GitHub): a self-hosted document archive, **GPL-3.0**, Docker-deployable, built specifically around "transform physical documents into a searchable online archive." It performs OCR on ingest and indexes the extracted text for full-text search, plus supports tags/correspondents/document-types as classification metadata — structurally close to what a correspondence registry needs, but it is a *personal/small-team* archive tool, not a multi-tenant, workflow-integrated registry with registration numbers and execution control. Its own docs warn it should "never run on an untrusted host" since documents are stored unencrypted at rest — a real caveat for a system holding official/PII-bearing correspondence, meaning encryption-at-rest would need to be added if any of its components were reused.
- **OCRmyPDF** (MIT license, the OCR engine Paperless-ngx itself wraps): takes a scanned PDF and adds an invisible, searchable text layer over the original image — the document still looks and prints identically, but becomes full-text-searchable and copy-pasteable. This is the right unit to adopt, not the whole Paperless-ngx product.
- **Tesseract OCR** (Apache 2.0, Google-maintained): the underlying OCR engine both of the above use. It has trained language data for Russian and Uzbek (Latin script has reasonable Latin-alphabet coverage via generic Latin models; native Uzbek Cyrillic and Uzbek Latin trained data exist but are less mature than major-language models) — **flag this as a real accuracy risk** worth a pilot test on actual scanned Uzbek/Russian government letters before committing, rather than assuming OCR quality will match English-language benchmarks.
- **Recommended architecture**: on ingest of any scanned attachment, run OCRmyPDF (or an equivalent Tesseract-based pipeline) to bake a text layer into the stored PDF, then index the extracted text in the same full-text search index used for the wiki layer (Postgres full-text search is sufficient at 23-person/departmental scale; Meilisearch or a similar lightweight search engine if search UX needs to feel more Notion-like with typo-tolerance and instant results). This makes "search for a letter by content, not just by registration number or subject line" possible from day one — directly closing the "findability" gap the base report itself raises for wikis (§1) but never extends to correspondence.
- **[ADOPT]** OCRmyPDF (or a Tesseract-based equivalent) as a mandatory ingest-time step for any scanned attachment, feeding a full-text search index — this is the single highest-leverage fix for the "registration + search on incoming letters is metadata-only" problem the editorial review flagged.
- **[AVOID]** Adopting Paperless-ngx as a product — its single-tenant, unencrypted-at-rest, non-workflow-aware design fights both the multi-tenancy ambition and the execution-control primitive that is this dimension's core feature; borrow its OCR pipeline pattern only.
- **[ADAPT]** Pilot OCR accuracy specifically on Uzbek Latin/Cyrillic and Russian scanned samples before relying on it for anything beyond "make it searchable" — do not assume production-grade accuracy for auto-extracting structured fields (registration numbers, dates) from OCR text without validation.

### E. Document classification / sensitivity tiers

The reference prototype already establishes the pattern this dimension should extend: its People directory implies **"field-level privacy (public work profile vs restricted HR record)"** — i.e., the same person-record has both a publicly-visible slice and a restricted slice, not one binary "private/public" flag on the whole record. Documents/correspondence need the identical shape, not a parallel scheme invented from scratch:

- **Recommended tiers** (extending the People-directory pattern, kept to the minimum a 23-person department actually needs — do not over-engineer a 4- or 5-tier national-security classification system that nobody will apply correctly): **Public** (can be shared outside the department without review — published reports, public-facing announcements), **Internal** (default — visible department-wide, not for external sharing), **Restricted** (visible only to the document's named participants — requester, approver chain, executor(s), and their direct managers; this is where most HR-adjacent correspondence, personnel orders, and anything referencing a named citizen's personal data belongs).
- **Mechanics**: classification is a required field at document creation (default `Internal`, escalate consciously — never silently defaults to the most sensitive or most open tier), inherited by any instruction/resolution attached to the document, and enforced at the query layer (a `Restricted` document simply does not appear in another user's search results or control-list, rather than appearing with a "no access" click-through — the reference prototype's own privacy-tier pattern for People implies the same "don't even show it exists" posture for the restricted tier).
- **Redaction ties in directly here** (see §B): moving a `Restricted` document to a lower tier for wider sharing is exactly the workflow OnlyOffice's redact tool exists for — blank out the personal-data fields, then reclassify the redacted copy as `Internal`/`Public`.
- **[ADOPT]** A required, inherited, query-enforced classification field (Public/Internal/Restricted) on every document and every instruction derived from it, built as a direct extension of the reference prototype's existing People-directory privacy-tier pattern — this is a small schema addition now that becomes very expensive to retrofit once real correspondence volume exists.

### F. National SSO / ONE ID integration

Uzbekistan does operate a national digital-identity layer distinct from (but adjacent to) E-Imzo, and it belongs in the E-Imzo section's neighborhood since both are pieces of the same "prove who this civil servant/citizen is" problem:

- **MyID** (also referred to as ONE ID in some materials, operated by **UZINFOCOM**, verified via its own site): a biometric facial-recognition identity-verification platform, drawing its source-of-truth data from the State Center for Personalization and the Ministry of Internal Affairs, with **data housed in UZINFOCOM's own data center** (i.e., already data-localization-compliant by construction). It claims 19M+ users and 280M+ authorizations, and is integrated into 31 commercial banks plus numerous government-service and payment-system logins. Integration surfaces: a MyID mobile app, Mobile SDK, Web SDK, Server SDK, and "MyID Cloud," with technical docs at `docs.myid.uz`.
- **Distinction from E-Imzo**: MyID/ONE ID answers "is this the person they claim to be" (biometric identity/authentication, analogous to a national SSO/KYC layer); E-Imzo answers "did this specific person cryptographically sign this specific document" (PKI non-repudiation). A mature integration uses **both**: MyID/ONE ID (or the department's existing internal-staff SSO, if the ministry runs its own) for day-to-day login to the platform, and E-Imzo specifically at the signing step for anything that must be legally binding when it leaves the department.
- **Caveat**: this pass could not reach either `single-sign-on.uz` (DNS failure) or `my.gov.uz/en/page/oneid` (404) directly to confirm the exact API/OAuth surface for third-party civil-servant login (as opposed to citizen-facing bank/service-provider KYC, which is what MyID's own marketing page emphasizes) — **this needs direct technical engagement with UZINFOCOM or the ministry's IT security team** before assuming MyID is the correct login mechanism for *internal staff* authentication (it may be citizen/customer-facing KYC infrastructure rather than a staff-SSO product; the ministry may instead run its own internal Active Directory/LDAP or a government-employee-specific identity system that this pass did not surface).
- **[ADAPT]** Design the platform's auth layer with a pluggable identity-provider boundary (OAuth2/OIDC-shaped) from day one, so that whichever staff-identity source the ministry actually mandates — MyID/ONE ID, an internal AD/LDAP, or a ministry-specific SSO — can be wired in without a rearchitecture; do not hardcode a single login mechanism.
- **[ADOPT]** Treat E-Imzo (signing) and a national/ministry identity layer (login/authentication) as two separate, both-necessary integrations rather than assuming one covers the other.

### G. Multi-tenancy implications for the WorkItem model and registration numbering

The base report's §9 WorkItem design and the registration-numbering scheme in §7 are specified single-department, despite the platform's explicit cross-ministry ambition. This needs resolving before, not after, the schema is built:

- **Tenant scoping**: `WorkItem` needs an explicit `tenant_id` (or `department_id`/`ministry_id`) from day one, even while only one department uses the platform — retrofitting a tenant column onto a live registration-number sequence later is exactly the kind of migration that risks corrupting the one thing (the registration number) civil servants trust as permanent and immutable.
- **Registration-number sequencing**: the CIS "входящий/исходящий №" pattern is inherently **per-organization** in real bureaucratic practice — each ministry/department keeps its own incoming/outgoing sequence, reset annually, and a document's true identity is (`organization`, `year`, `direction`, `sequence number`), not a bare integer. The multi-tenant schema should mirror this directly: the sequence counter is scoped per-tenant-per-year-per-direction, never a single global counter — a global counter would be both wrong (doesn't match how registration numbers are legally understood) and a needless cross-tenant contention point.
- **Cross-tenant visibility**: the "control list" (overdue instructions dashboard) and search must default to **tenant-isolated** — a department in one ministry must never see another ministry's or department's WorkItems by default. The one legitimate cross-tenant case is a *parent-organization oversight view* (e.g., the ministry level seeing a rolled-up status across its departments) — this should be modeled as an explicit, permissioned hierarchy relationship between tenants, not implicit shared visibility.
- **Template scoping**: the 4-6 native government document templates (memo, letter, protocol, order, report, business-trip order) should ship as a **shared base catalog** every tenant gets by default, with each tenant able to add tenant-specific templates on top — avoids every new department/ministry re-inventing the same six documents from scratch (defeats "zero training" for a new tenant) while still allowing local customization (letterhead, specific approval chains).
- **[ADOPT]** Build `tenant_id` and a per-tenant-per-year-per-direction registration sequence into the WorkItem schema from the very first version, even for a single-department launch — this is materially cheaper to build in from day one than to retrofit once real registration numbers exist in production.
- **[ADAPT]** Model cross-tenant oversight (a ministry seeing its departments' rollups) as an explicit permissioned hierarchy edge between tenants, not a shared-visibility default — default to strict tenant isolation and open it up only where an actual reporting-line relationship exists.

### H. Mobile / approval fallback beyond Telegram

The base report leans entirely on Telegram inline-button approval (§9) without addressing what happens when Telegram is unavailable to a given official — a real scenario, since some government agencies restrict Telegram on work devices/networks even though it is the dominant consumer messenger in Uzbekistan, and Telegram's own infrastructure is not hosted in-country (already flagged as an open question in the base report, but with no fallback design offered):

- **Layered fallback design** (mirroring how mature approval products like Lark Approval and enterprise MDM-restricted orgs actually handle this): (1) Telegram inline buttons as the primary, fastest path where allowed; (2) a **PWA** (installable, offline-tolerant web app) as the always-available fallback that works on any device with a browser, using **Web Push** (or Firebase Cloud Messaging for Android reach) for notifications when Telegram isn't an option; (3) an **email digest with a signed one-click magic-link** (approve/reject without a password prompt, token-scoped and short-lived) as the lowest-common-denominator fallback that works even without a smartphone.
- **Why not a native app first**: building and maintaining separate iOS/Android native apps is a heavy commitment for a 23-person department's tool that explicitly wants to avoid "Jira-level" overhead; a PWA gets installable-icon/home-screen presence and push notifications on Android without an app-store submission process, and degrades gracefully to "just a website" on any device that doesn't support PWA install — the pragmatic middle ground given the resourcing reality.
- **SMS as a last-resort channel**: for officials who are difficult to reach digitally at all, a local telecom SMS gateway (Beeline/Ucell/Uzmobile all offer bulk-SMS APIs) sending "You have an approval waiting, reply APPROVE/REJECT [code]" is a viable, low-tech fallback worth keeping in the design even if it's rarely the primary path — it costs little to support and covers the edge case where a manager is traveling with only basic connectivity.
- **[ADOPT]** A PWA with Web Push as the non-Telegram fallback for approvals, built from the same underlying WorkItem/approval API Telegram's bot uses — treat Telegram as one notification channel among several against a shared approval-action endpoint, not the only front door.
- **[ADAPT]** Signed one-click email magic-links as a secondary fallback for officials without reliable app/push access — lower friction than "log into a portal," consistent with the base report's own "never make someone log in just to approve" principle (§ TL;DR point 4), just via a different channel.
- **[AVOID]** Building native iOS/Android apps for v1 — disproportionate engineering cost for a 23-person department relative to a PWA that covers the same fallback need.
