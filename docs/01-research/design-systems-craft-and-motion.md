# Design systems, visual craft, motion, and delightful apps

**TL;DR:** The 2025–2026 state of the art is converging on a stack — Tailwind CSS v4 (OKLCH, CSS-first tokens) + shadcn/ui-style copy-in components on Radix or the newer Base UI primitives + DTCG-format design tokens (spec went stable Oct 2025) — that gives small teams Jira-grade capability without Jira-grade lock-in or bloat. Craft leaders (Emil Kowalski at Linear, Rauno Freiberg) converge on the same message: restraint, not decoration — animate with purpose, respect `prefers-reduced-motion`, use skeletons only for 1–10s waits. The one finding specific to us: Uzbek's `Oʻ`/`Gʻ`/tutuq belgisi apostrophe characters have a real Unicode-encoding trap that "supports Cyrillic" font claims do not cover — this needs explicit testing before font selection. Government reference points split into two camps — GOV.UK/Estonia (spartan, trust-through-plainness) vs Diia (app-store-grade polish) — and our own future peer, my.gov.uz, already shows the gap between a decent visual shell and a broken basic feature (its search returned "no results" live). The concrete recommendation is a copy-in component library, not a framework: own the code, theme it with tokens, and spend craft budget on the 15 components civil servants touch every day, not on a bespoke design system.

## 1. The component-library landscape: own your code, don't rent a framework

The single biggest shift since 2023 is the move away from installing a component library as an npm dependency and toward **copying component source into your own repo**, then customizing it. shadcn/ui popularized this ("this is not a component library, it is how you build your component library") and it has kept expanding: recent changelog items include a standalone `cn` utility package (Sep 2026), **private GitHub registry support** so an org can host its own internal component registry gated by `GH_TOKEN`/GitHub CLI auth (Aug 2026), server-side registry search for large catalogs (Jul 2026), and even AI-agent-facing components (a `Questionnaire` component for onboarding/clarification flows, "human-in-the-loop" scripted flows via `@shadcn/helpers`, Aug 2026) — signalling that shadcn now explicitly targets both human UI and agent-driven UI in the same registry model [shadcn/ui changelog].

Underneath shadcn sits a primitives layer, and here there are now three real choices, not one:

| Library | Who builds it | Philosophy | License | Notable |
|---|---|---|---|---|
| **Radix Primitives** | Originally Colm Tuite/Radix; now WorkOS-sponsored | Unstyled, accessible, one component per package | MIT | The incumbent; shadcn's original default; large ecosystem, but community reports of a slower release cadence prompted the Base UI effort |
| **Base UI** | MUI's dedicated 7-person team (with Radix and Floating UI lineage) | "Future-proof foundation," WCAG 2.2, ARIA APG patterns | MIT | Newer (2024–2025), actively/aggressively maintained; adds harder components Radix lacks (Combobox, Autocomplete, input scrubbing, nested dialogs); intentionally API-similar to Radix for easy migration [base-ui.com] |
| **Ark UI** | Chakra Systems (built on the Zag.js state-machine engine) | True headlessness, state-machine-driven predictability | MIT | 45+ components; **one API across React, Vue, Solid, and Svelte** — the only one of the three offering true multi-framework parity; powers Chakra UI and Park UI [ark-ui.com] |

For us: shadcn now ships CLI support for Base UI and Ark as alternate "styles," so the practical decision is primitives, not registry — and it can be revisited later without rewriting the UI layer, because the copy-in components are already yours.

Styling foundation: **Tailwind CSS v4** (shipped 22 Jan 2025) is a ground-up rewrite — full builds ~3.78x faster, incremental rebuilds with new CSS ~8.8x faster, incremental rebuilds with no new CSS ~182x faster (192µs), CSS-first configuration via an `@theme` block instead of `tailwind.config.js`, native `@import "tailwindcss"` with zero config, and — critically for this report — **all design tokens are generated as real CSS custom properties automatically**, and the default color palette moved from sRGB to **OKLCH** for a wider, more vivid gamut. It also picked up container queries without a plugin, `@starting-style` for enter/exit transitions (no JS needed for simple appearance animations), `color-mix()`-based opacity utilities, and logical properties for RTL support — worth noting given Uzbek/Russian are LTR but a future Arabic-script tenant is not impossible [tailwindcss.com/blog/tailwindcss-v4].

## 2. Design tokens: the DTCG spec is no longer a draft

The W3C Design Tokens Community Group format reached **stable status at version 2025.10 (28 Oct 2025)**, after years of editor's drafts going back to 2021. It defines a shared JSON structure for tokens (color, dimension, typography, etc.) so that Figma, Tokens Studio, Style Dictionary, Adobe, Sketch, Penpot and dozens of design systems can exchange the same source of truth instead of hand-translating [github.com/design-tokens/community-group]. Practically this means: define tokens once in DTCG JSON, run them through **Style Dictionary** to emit Tailwind v4 `@theme` CSS variables, and the same source can later emit tenant-specific overrides (a different ministry's primary color) without touching component code — this is the mechanism that makes "multi-tenant" real rather than aspirational.

**OKLCH in practice.** Radix Colors — a complementary system to Radix Primitives — builds each hue as a **12-step scale** (step 1–2 = app backgrounds, 3–5 = component backgrounds/hover/active, 6–8 = borders/separators, 9–10 = solid backgrounds, 11–12 = text), targets contrast using the **APCA algorithm** rather than old WCAG-2 ratios, and is P3-gamut aware with matching transparent (alpha) variants for blending across light/dark. Switching themes is a single class toggle on a container [radix-ui.com/colors]. This 12-step, role-based scale (not "primary-500") is the right mental model to copy for our own green/amber/slate-blue/plum sub-department palette from the reference prototype — it turns "pick a color" into "pick a step," which a non-designer engineer can do consistently.

**Contrarian note on OKLCH:** it is real progress (perceptually uniform lightness, wider gamut) but it is not free — very old browsers need fallbacks, and pushing chroma too high in the mid-lightness range clips/hue-shifts on non-P3 monitors, which is exactly the kind of hardware likely to be standard-issue in a ministry office. Test the palette on ordinary sRGB monitors before finalizing, not just on designers' MacBooks.

## 3. Typography — and the Uzbek-specific trap

- **Inter** (Rasmus Andersson): SIL OFL 1.1, free/open, "147 languages... over 2,000 glyphs," full Latin diacritics + Greek + **Cyrillic**, variable weight 100–900 with three optically-distinct masters (100/400/900), true italics, extensive OpenType features (tabular figures, stylistic sets). Used everywhere from interfaces to "NASA instrumentation" — the safest, most battle-tested default [rsms.me/inter].
- **IBM Plex**: OFL, explicitly built for UI/enterprise contexts over a 2-year design process; Sans/Serif/Mono/Condensed/Math variants; script coverage spans Latin, **Cyrillic**, Arabic, Greek, Hebrew, Thai, Devanagari, and CJK — the broadest coverage of the three, useful if this platform ever needs Arabic-script or CJK tenants [github.com/IBM/plex].
- **Geist** (Vercel): confirmed to exist as Geist Sans/Mono; **we could not confirm Cyrillic coverage this session** — treat as unverified and do not select it for a Uzbek/Russian product without checking its glyph table directly.

**The real finding:** the Uzbek Latin alphabet's `Oʻ` and `Gʻ` (distinct phonemes, not "O + apostrophe" as decoration) and the tutuq belgisi glottal-stop mark (`sanʼat`, `maʼno`) are correctly encoded with **U+02BB MODIFIER LETTER TURNED COMMA** and **U+02BC MODIFIER LETTER APOSTROPHE** respectively — but "these characters are absent from most keyboard layouts... and many fonts," so in practice almost everyone substitutes the plain **U+2018 left single quote** or **U+0027 apostrophe** instead [en.wikipedia.org/wiki/Uzbek_alphabet]. This is confirmed live on the ground: **my.gov.uz**, Uzbekistan's own unified government portal, ships in four languages (Oʻzbekcha, Русский, English–BETA, Qaraqalpaqsha–BETA) [my.gov.uz]. This is not a cosmetic detail — it affects search/sort correctness (does "Oʻzbek" sort/match the same as "O'zbek"?), form validation regexes, and font glyph testing. **Action: pick the actual code points our data layer will normalize to (recommend: normalize storage to U+02BB/U+02BC, but accept and transliterate the common straight-quote input at the UI edge), and verify the chosen font renders both code points correctly at the weight/size used in body text — do not assume "Cyrillic support" implies this.**

## 4. Dark mode, density, and the editorial-vs-product tension

Modern dark-mode practice (visible across shadcn, Radix Colors, Tailwind v4) is **token-driven, not color-inverted**: define semantic tokens (`--background`, `--foreground`, `--card`, `--border`, `--ring`) and swap the underlying OKLCH/Radix-scale values per theme class, never literally invert hues. Our reference prototype already does this correctly (light warm-paper theme + a separately-tuned dark forest-green sidebar theme, not one auto-inverted from the other) — worth preserving as a rule: **every themeable surface gets its own hand-tuned dark value, not a CSS filter.**

**Density** is the other axis power users need and first-timers don't: Attio's homepage demonstrates the pattern directly — dense multi-column tables (company name, ICP score, assignee, deal stage, value, all visible at once) aimed at "power users managing complex revenue operations," paired with a "connect your inbox, it builds itself" low-friction onboarding path for new users [attio.com]. That is close to a template for our own tension: **comfortable density as default, a compact/dense toggle for the Data & BI Analytics sub-department**, not two different products.

**Editorial + institutional aesthetics coexisting with a fast product UI** is achievable and has precedent in exactly the direction the reference prototype already points: warm paper background, serif display headings, small-caps eyebrow labels, deep green as the institutional color — layered *on top of* an otherwise conventional Tailwind/shadcn interaction layer (buttons, tables, forms behave exactly as users expect from any modern SaaS app). The mistake to avoid is letting "institutional" bleed into the interaction model itself (e.g., multi-step wizards instead of inline edits, or ornamental chrome that slows scanning) — the identity should live in typography and color tokens only, never in behavior.

## 5. Motion: the craft consensus is restraint

Two names dominate current thinking on interface motion, and both work at/near Linear:

- **Emil Kowalski** (Design Engineer at Linear, ex-Vercel) runs **animations.dev**, a $249 course (with a 60% PPP discount for lower-income countries — relevant, Uzbekistan likely qualifies) covering animation theory (easing, springs, timing, "taste"), CSS animation, Motion/React implementation, and real component walkthroughs (drawers, nav menus, SVG) [animations.dev]. His writing is consistently anti-decoration: essay titles like **"You Don't Need Animations"** and **"7 Practical Animation Tips"** argue that most interface motion should be justified by feedback or continuity, not delight-for-its-own-sake [emilkowal.ski]. He also authors two of the most-used unstyled components in the ecosystem: **Sonner** ("an opinionated toast component for React" — types include default/success/info/warning/error/action/promise/custom, position-aware swipe direction, `visibleToasts` cap, headless mode) [sonner.emilkowal.ski], and **Vaul**, a React drawer component (iOS-style bottom sheet pattern is the well-known convention, though we could not re-confirm snap-point specifics from the live docs this session) [vaul.emilkowal.ski].
- **Rauno Freiberg**'s portfolio-as-manifesto ("Craft") demonstrates rather than lectures: recurring themes are **microinteractions** ("invisible details of interaction design"), motion as **feedback embedded in state, not bolted on after**, and using **animation to mask perceived latency** (motion starts before the real result is ready) [rauno.me/craft].

**Engine layer:** **Motion** (the project formerly known as Framer Motion, now framework-agnostic) is a "hybrid engine" mixing JS-driven and hardware-accelerated browser APIs, claims API surface "up to 90% smaller than the GSAP alternative," ships real spring physics, supports React/Vue/vanilla JS, and as of recent releases wraps the native **View Transitions API** with a simplified API ("a View Transition API for the rest of us"). It is MIT-licensed and used in production by Framer and Figma at scale [motion.dev].

**Platform primitives:** the native **View Transitions API** now supports both same-document (SPA, `document.startViewTransition()`) and cross-document (MPA, opt in per-page via the `@view-transition` CSS at-rule, driven by `pagereveal`/`pageswap` events) transitions, is considered broadly usable, and removes the old need to keep old/new DOM in sync manually [MDN]. **`prefers-reduced-motion`** has been supported in all major browsers since January 2020 — the rule is to *replace* motion-heavy transitions with subtler ones (opacity instead of scale/pan), not delete feedback entirely, and to keep the reduced-motion CSS rule at equal-or-higher specificity later in the cascade so it reliably overrides [MDN].

**Recommendation for our motion budget:** 150–250ms for micro-interactions (hover, toggle, toast enter), CSS transitions/`@starting-style` for simple cases, Motion/React only where springs genuinely help (drag-to-reorder, drawers), View Transitions API for page-level navigation once browser baseline is confirmed, and a hard `prefers-reduced-motion` fallback everywhere — a government tool must never feel like it's "performing."

## 6. Loading states, command menus, tables, icons

**Skeletons vs. spinners** (NN/g guidance): **under 1 second, show nothing** — any loading UI at that speed reads as flicker/annoyance; **1–10 seconds**, spinners for single modules (a card, an embed) and skeleton screens for full-page loads (skeletons reduce *perceived* wait by previewing layout and lowering cognitive load, but only if they mirror real content structure — a header/footer-only "frame" skeleton is explicitly called out as ineffective and should not be used); **over 10 seconds**, use a real progress bar with an estimate, not an indefinite spinner. Animated skeletons can themselves cause distraction/accessibility issues, so keep the shimmer subtle and respect reduced-motion [nngroup.com].

**Command menu:** **cmdk** (by Paco Coursey, powering Vercel's own command menu/autocomplete) is the de facto standard — composable, minimally-styled (data-attribute hooks, not a CSS framework), Cmd/Ctrl+K is now a near-universal convention across the products in this space, handles 2,000–3,000 items without needing virtualization, requires React 18+, and has no React Native path [github.com/pacocoursey/cmdk]. For a "zero-training" civil-servant audience, **the command palette must be a power-user accelerator layered on top of visible, mouse-discoverable navigation — never the only way to reach a feature.**

**Data tables:** **TanStack Table** is the standard headless engine (1.2B+ cumulative downloads across the TanStack family, 28k+ GitHub stars) — sorting, filtering, faceting, grouping/aggregation, row/column pinning, resizing, and virtual scrolling, all logic-only, paired with shadcn/ui's official "data table" recipe for the rendered UI [tanstack.com/table]. This is the right base for the Projects register and People directory — it scales from 23 rows today to a multi-tenant, thousands-of-rows future without a rewrite.

**Icons:** **Lucide** — 1,800+ icons, ISC license, strict single-stroke-weight consistency, 24px grid, tree-shakable per-icon imports, packages for essentially every framework, actively community-maintained [lucide.dev]. This is the safe, neutral default that matches shadcn's own default icon choice. Phosphor Icons and Hugeicons are real, larger alternatives (Phosphor's multi-weight system — thin/light/regular/bold/fill/duotone — is well known in the ecosystem) but **we could not independently re-verify current icon counts, weights, or licensing for either this session** (fetches failed) — verify directly before committing.

## 8. Recommended design-token starter kit

**Color (OKLCH, Radix-style 12-step semantic scales, one per sub-department + one neutral + one institutional-primary):**

| Token role | Step | Example (institutional green, light) |
|---|---|---|
| App background | 1–2 | `oklch(0.98 0.01 150)` |
| Card / surface | 2–3 | `oklch(0.99 0.005 150)` |
| Subtle border | 5–6 | `oklch(0.88 0.02 150)` |
| Solid UI (buttons) | 9 | `oklch(0.42 0.08 150)` — tuned to sit near the reference `#315b4c` |
| Solid hover | 10 | slightly darker/more chroma than step 9 |
| Text on solid | 12 (near-black or near-white per contrast) | `oklch(0.98 0 0)` |
| Body text | 12 | `oklch(0.22 0.02 150)` |

Ship a matching **dark** value set per role (hand-tuned, not inverted), plus 4 accent scales for the sub-departments (green/amber/slate-blue/plum from the reference), plus semantic status scales (success/warning/danger/info) independent of brand color.

**Type scale** (Inter as default, IBM Plex as fallback if Uzbek/Cyrillic edge cases demand broader coverage): 12/14/16(base)/18/20/24/30/36/48px, 1.5 line-height for body, 1.2 for headings, serif display face (Georgia-class, matching the reference's editorial mood) reserved for H1/page titles only.

**Spacing scale:** 4px base unit — 4/8/12/16/24/32/48/64/96.

**Radius:** `0.5rem` for controls, `0.85rem` for cards (matches the reference prototype's existing `--radius: .85rem` — keep it, it's already well-judged).

**Elevation:** 3 tiers only — flat (bordered, no shadow, default for cards on the paper background), raised (subtle shadow, for popovers/dropdowns), overlay (stronger shadow + backdrop dim, for modals/drawers).

**Motion:** durations 100ms (instant feedback: checkbox, toggle), 200ms (standard: hover, fade, toast), 300–400ms (spatial: drawer/dialog open, page transition); easing `cubic-bezier(0.22, 1, 0.36, 1)` (ease-out, the near-universal default for "settle" motion) for entrances, linear or ease-in for exits; always gated by `prefers-reduced-motion`.

## What this means for us

1. **[ADOPT]** shadcn/ui + Tailwind v4 as the component foundation, copied into our repo, not installed as a black-box package — future in-house or contracted developers can read and modify every component, which matters for a platform meant to be handed to other ministries.
2. **[ADOPT]** DTCG-format tokens (spec stable since Oct 2025) generated via Style Dictionary into CSS variables from day one — this is the actual mechanism that makes "multi-tenant, different ministry, different color" possible without forking the codebase.
3. **[ADAPT]** OKLCH for the primary palette, built as 12-step Radix-style scales — but validate the rendered colors on ordinary sRGB government-office monitors before finalizing; don't design only on wide-gamut laptops.
4. **[ADOPT]** Keep the reference prototype's editorial mood (serif headings, warm paper, deep green, small-caps eyebrows) as a thin identity layer over an otherwise conventional interaction model — this is exactly how GOV.UK and Diia keep interactions predictable while looking distinct.
5. **[AVOID]** Building a bespoke, from-scratch design system or component framework — a 23-person department with no dedicated design-systems team should not carry that maintenance burden; use Radix or Base UI as the accessibility/behavior layer.
6. **[ADOPT]** A Cmd/Ctrl+K command palette (cmdk) for power users, but never as the *only* path to a feature — a first-time civil servant must be able to do everything by clicking, per the brief's "zero training" requirement.
7. **[ADOPT]** NN/g's loading-state thresholds exactly: nothing under 1s, matched skeletons 1–10s, real progress bars beyond 10s (e.g., bulk exports/reports) — this alone will make the app feel faster than most government software without any actual performance work.
8. **[ADAPT]** Motion/React or plain CSS transitions for interface feedback, 150–250ms, ease-out, always gated by `prefers-reduced-motion` — the craft consensus (Kowalski, Freiberg) is restraint; a ministry tool that "performs" for the user will read as unserious.
9. **[ADOPT]** Vaul-style bottom drawers for mobile flows — Telegram's dominance in Uzbekistan means a meaningful share of usage will be phone-first, and bottom sheets are the pattern users already know from Telegram/consumer apps.
10. **[ADOPT]** Inter as the default UI typeface (open license, confirmed Cyrillic, huge language coverage) — but treat this as provisional until item 11 is resolved.
11. **[AVOID]** Assuming "supports Cyrillic" equals "supports Uzbek correctly" — explicitly test the exact code points for `Oʻ`/`Gʻ`/tutuq belgisi (U+02BB, U+02BC) in the chosen font and decide a normalization strategy (store correct Unicode, accept straight-quote input) before any content is entered at scale.
12. **[ADOPT]** TanStack Table + shadcn's data-table pattern for Projects/People — headless, virtualization-ready, scales from 23 rows to a multi-ministry future without a rewrite.
13. **[AVOID]** Building Phase 3 "decision intelligence" dashboard components (forecasting, workload balancing) before Phase 1 reliability is solid — the reference roadmap itself sequences this correctly; don't let UI ambition outrun it.
14. **[ADAPT]** Treat my.gov.uz's live broken-search bug as the cautionary benchmark: budget disproportionate QA time on the boring core loop (search, save, list, filter) — a government audience has near-zero tolerance for basic breakage, unlike a startup that can patch in public.
15. **[ADOPT]** A comfortable/compact density toggle at the table level early — it is the cheapest way to serve both a first-time HR-adjacent user and a power user in Data & BI Analytics from one codebase, which is the brief's central tension in miniature.

## Gap-fill addendum

This addendum reports back on the eight gaps identified in the editor's verification pass (§ Editor's verification notes, below). Web search was unavailable this session (budget exhausted before any query ran), so all findings here come from direct WebFetch reads of primary sources — 12 fetches across the 10 gap topics, listed with the rest in Sources.

**Linear's own color methodology — thinner than assumed, and not actually "OKLCH-branded."** Fetching Linear's own design-refresh post directly [linear.app/now/behind-the-latest-design-refresh, Mar 2026] shows Linear does not publicly brand its process as "OKLCH" or "LCH" the way Radix Colors does. What they describe is an **internal color-picker tool exposing hue/chroma/lightness controls per token** — chroma and lightness are LCH-family terms (not HSL's saturation/value), so the underlying model is almost certainly a perceptual space even though Linear never names it — used to shift their whole palette "from a cool, blue-ish hue" toward "a warmer gray that still feels crisp, but less saturated," with final token values exported as JSON and synced to Figma via a custom plugin. A second, more recent post (title only, from the blog index) — **"Styling Linear for the future with StyleX"** [linear.app/now/styling-linear-for-the-future-stylex, Aug 2026] — signals Linear moved its styling layer to Meta's StyleX for tooling/build reasons, "designing clearer boundaries for both humans and agents," which is a build-system story, not a color-methodology one. **Correction to how the brief's assumption should be read:** Linear's actual practice is closer to our own report's Radix-Colors recommendation than to a distinct methodology worth copying — a bespoke internal color-tuning tool is a craft-team luxury (Linear has dedicated design engineers), not something a 23-person department should build; the *outcome* (hue/chroma/lightness tuned per role, exported once, consumed everywhere) is exactly what Style Dictionary + DTCG tokens already gives us for free. [AVOID] building a bespoke internal color-picker tool à la Linear — [ADOPT] the same end-state (perceptually-tuned, role-based tokens synced once between design and code) via the DTCG/Style Dictionary pipeline already recommended in §2.

**Illustration and empty-state style — two real options, and a representation trap to avoid.** Two open-license illustration systems dominate this space and sit at opposite ends of the tone spectrum. **Humaaans** [humaaans.com], by Pablo Stanley, is a CC0 "mix-and-match" library of modular human figures (interchangeable hair, clothing, poses) explicitly used across the industry for "empty, error, and success state screens, onboarding sequences, and landing pages" — friendly and characterful, but every figure is a *person*, which for a government platform means implicit choices about who is depicted (gender, dress, ethnicity) that a ministry product should not be making casually. **unDraw** [undraw.co], by Katerina Limpitsouni, is the more institutional-fit alternative: minimalist line-art SVGs with "subtle shadows & multi-level objects," and critically, a **live single-color recolor tool** — "customize your main color on-the-fly and simply click download" — so every illustration can be tinted to the exact institutional-green token (step 9 from §8) rather than shipping with its own clashing default palette; no attribution required, free for commercial use. **Recommendation:** unDraw-style single-brand-color line art for our empty states (no-data lists, unassigned tasks, empty search results), reserving any human-figure illustration (if used at all, e.g. onboarding) for careful, deliberate case-by-case review rather than a bulk mix-and-match library. Pair every illustration with the pattern already listed in §9 item 9 (icon/illustration + one-line explanation + primary action) and keep illustrations monochrome-tinted, never full-color stock art that fights the OKLCH token palette. [ADOPT] unDraw-style single-color-tintable line art, tinted to the institutional-green token, for all empty/zero-data states. [AVOID] multi-color stock illustration sets or mix-and-match human-figure libraries as a default — the representation and palette-clash risk outweighs the personality gain for a ministry tool.

**Resizable sidebar — a real, small, unmaintained-risk-free library, not a gap to leave open.** **react-resizable-panels** [github.com/bvaughn/react-resizable-panels], by Brian Vaughn (a former React core team member — Profiler/DevTools author), is MIT-licensed, has 5.4k GitHub stars/226 forks, and ships a `Group`/`Panel`/`Separator`-style API (framework docs call the actual exports `PanelGroup`/`Panel`/`PanelResizeHandle`) for horizontal or vertical resizable layouts. Panels accept percentage, pixel, `em`/`rem`, or viewport units; a `defaultLayout` prop persists sizes "between page reloads" (i.e., wire it to `localStorage` per-viewer, matching this report's existing browser-storage guidance elsewhere in the project); separators carry WAI-ARIA roles for keyboard resize; both `Group` and `Panel` expose refs for imperative collapse/resize. This is the natural pairing with §9 item 1's collapsible sidebar: **collapsible for the binary icon-only state, resizable (via this library) for users who want a wider Projects/People list pane** — exactly the brief's "collapsible, resizable" phrase, now with a named implementation. [ADOPT] react-resizable-panels for any split-pane layout (sidebar, and later a master-detail Projects/People view) — small, MIT, actively maintained, keyboard-accessible by default.

**Layout shells — Vercel's Geist fills the one named gap the report left at zero.** Vercel's own design system, **Geist** [vercel.com/geist/introduction], is confirmed live: it standardizes a "high contrast, accessible color system," typography on Geist Sans/Mono (already cited in this report for the Cyrillic-coverage caveat), "materials" (radii, fills, strokes, shadow presets), and a grid-based layout described as "a core part of the Vercel aesthetic" — published as installable React components (`@vercel/geistcn`, itself a shadcn-style copy-in registry, not an npm black box). This directly reinforces this report's central recommendation: Vercel, the company behind cmdk and Geist fonts already cited here, also runs its own dashboard on the exact "own-your-components, token-driven" model this report proposes for us — a second real-world validation of the approach beyond Attio's. The other 11 named products (Raycast, Notion, Height, Arc, Amie, Things 3, Craft, Family, Campsite, Cal.com, Notion Calendar/Cron) remain unfetched this pass too — WebFetch works one URL at a time and budget was prioritized toward the eight named gaps and four adjacent topics; a dedicated hands-on session (as the Open Questions already recommend) is still the right way to close that specific survey. [ADOPT] Geist as a second reference point (alongside Attio) for "power tool, grid-disciplined, token-driven" shell design; [ADOPT] the copy-in-registry model Geist itself uses (`@vercel/geistcn`) as further validation of this report's shadcn-style recommendation.

**Singapore's government design system — a closer analogue than GOV.UK or Diia, and directly validates our token pipeline.** The **Singapore Government Design System (SGDS)** [designsystem.tech.gov.sg], built by GovTech Singapore under the mission "Unifying Government through Design and Code," is the missing government reference the brief named. Two things make it unusually relevant to us, more so than GOV.UK or Diia: (1) its stated philosophy is explicitly **"design once, use everywhere"** with a shared component core (`sgds.js`) ported across **React, Vue, Angular, Svelte, and vanilla JS** — the same multi-framework ambition Ark UI offers at the primitives layer (§1) but proven here at whole-of-government scale; and (2) it **converts SGDS design tokens into Tailwind CSS v4** directly — i.e., a national government has already built and shipped the exact DTCG-tokens-to-Tailwind-v4 pipeline this report recommends in §2, at multi-agency scale, which is the strongest available evidence that our own multi-tenant token plan (Open Questions, "no concrete multi-brand implementation example was verified") is not a novel bet. Its color foundations page [designsystem.tech.gov.sg/foundations/colour] states three principles — **hierarchical** (color signals interaction/prominence), **legible** (WCAG-referenced contrast), **harmonious** (consistent role-to-color mapping) — plus a concrete rule worth copying directly: **skip at least one step in the scale when pairing foreground/background colors** for guaranteed separation, and grays are built on "a perceptually curved progression of lightness" (10 tints/shades per theme) rather than linear steps. The page did not state which specific citizen-facing products (Singpass, LifeSG) currently run on SGDS, so that adoption claim is left as unconfirmed rather than asserted. [ADOPT] SGDS as the primary government reference point going forward, ahead of GOV.UK/Diia/Estonia for our purposes, specifically because it validates the Tailwind-v4-plus-DTCG-tokens multi-tenant pipeline at government scale. [ADOPT] the "skip a step" foreground/background pairing rule as an explicit addition to our own Radix-style 12-step scale usage (§2, §8).

**Data-table aesthetics — shadcn's own recipe is deliberately minimal, and sticky headers are a gap we must fill ourselves.** Reading shadcn's data-table docs directly [ui.shadcn.com/docs/components/data-table] surfaces the actual visual conventions the headless TanStack engine (§6) ships with by default: the table sits in an `overflow-hidden rounded-md border` container (a bordered card, not a bleeding-edge table — consistent with this report's "flat, bordered, no shadow" elevation tier from §8); row selection is exposed as a `data-state="selected"` attribute for CSS targeting rather than an inline style; sort direction is communicated with `ArrowUpDown`/`ArrowUp`/`ArrowDown` icon swaps in the header cell (a Lucide-compatible icon set, §6); the selection column uses a header "select all" checkbox plus per-row checkboxes with a "0 of 5 row(s) selected" status line; the footer pagination uses outline-variant buttons, a "Rows per page" dropdown (10/20/25/30/40/50), and compact `h-8 w-8 p-0` icon-button sizing throughout — i.e., the recipe already defaults to a **compact, not comfortable, density** out of the box, which is the opposite of what §4's density guidance assumes as default. **What the recipe does not address at all: sticky headers.** For the Projects register and People directory (both expected to scroleable to hundreds of rows), a plain scrolling `<table>` loses its header — this needs an explicit `sticky top-0 bg-background z-10` treatment on `<TableHeader>`, which is not part of the official recipe and must be added by us. [ADOPT] shadcn's data-table visual conventions (bordered container, data-state row styling, icon-driven sort affordances, compact pagination controls) as the starting point. [ADAPT] override the recipe's default compact density to match our comfortable-default-with-toggle decision from §4/§8, and explicitly add sticky headers — this is real engineering work the recipe doesn't hand us for free.

**Accessibility compliance process — a real methodology exists, but no confirmed Uzbekistan-specific legal mandate.** The W3C Web Accessibility Initiative's own evaluation guidance [w3.org/WAI/test-evaluate] is explicit that **compliance is a process, not a one-time score**: evaluate "early and throughout the development process," start with "Easy Checks" (a first review runnable by non-specialists), use automated tools only as a floor (WAI's own tool directory lists 100+, but "no tool alone can determine if a site meets accessibility standards"), require **knowledgeable human evaluation** including actual screen-reader and keyboard-only testing, and — for a rigorous conformance claim — follow the structured **WCAG-EM (WCAG Evaluation Methodology)**, which also recommends **involving real users with disabilities** in evaluation rather than relying on internal testing alone. This page did not state any Uzbekistan-specific legal accessibility mandate, nor did it reference EN 301 549 or ADA as applicable frameworks — those are EU/US-specific and their applicability to a Uzbek government platform is unconfirmed and should be a direct policy question, not an assumption; this has been added to Open Questions below. [ADOPT] a lightweight recurring practice, not a single audit: automated linting (axe-core or equivalent) in CI as a floor, plus a periodic manual pass with an actual screen reader (NVDA is free and the most realistic proxy for a Windows-desktop government audience) and keyboard-only navigation on the 15 components from §9, before assuming WCAG AA is met just because Radix/Base UI primitives are "accessible by default."

**i18n/l10n mechanics — ICU MessageFormat is the standard, and Russian's plural rules are a real, solvable requirement, not just a formatting nuance.** **next-intl** [next-intl.dev], the leading Next.js i18n library, is built on **ICU MessageFormat syntax** directly — its own docs show plural syntax like `{count, plural, =0 {No followers yet} =1 {One follower} other {# followers}}` — plus built-in `format.dateTime()`, `format.relativeTime()`, and `format.number()` (including currency) helpers that handle locale-specific formatting and timezones automatically, with both v3 and v4 currently documented. The library's own docs did not spell out Russian-specific plural handling in what we fetched, but this is where general ICU/CLDR knowledge fills the gap safely: the **Unicode CLDR plural-rules standard that ICU MessageFormat implements defines up to six categories — zero/one/two/few/many/other** — and Russian is a **"one/few/many/other"** language (e.g., 1 файл, 2–4 файла, 5–20 файлов, then the pattern repeats by last digit) which is meaningfully more complex than English's binary one/other and cannot be handled by simple `count === 1 ? ... : ...` string logic; Uzbek, by contrast, has no grammatical plural marking dependent on count in the way Russian does, which simplifies that side. **Action for us:** any string with a count (task counts, days-until-deadline, "N comments") must route through ICU MessageFormat's `plural` syntax from day one in all three locales, never string concatenation — retrofitting plural-correct Russian strings after launch is expensive. [ADOPT] next-intl (or any ICU-MessageFormat-based library) specifically because it forces plural-correct Russian from the start, not as a later patch.

**Design-to-code handoff — Figma Code Connect exists and fits our stack, but is gated to paid seats.** **Figma Code Connect** [developers.figma.com/docs/code-connect] solves exactly the handoff problem named in the brief: it maps real repository components to their Figma design-file counterparts so that opening a component in **Figma's Dev Mode shows the actual production code snippet** ("true-to-production code snippets from your design system") rather than a designer's approximation, with **Code Connect UI enabling one-to-many mappings** (one Figma component to multiple framework implementations) configurable by developers directly in Figma, without needing a dedicated design-ops role — a good fit for a team with no dedicated designers. The material constraint: Code Connect **requires a Dev or Full seat on Figma's Organization or Enterprise plan** — it is not available on Free or Professional plans, which matters for a government budget. The fetched docs did not describe any direct integration between Code Connect and Figma Variables/DTCG tokens (§2) — that connection is unconfirmed, not refuted, and should be checked directly against current Figma docs before assuming tokens and component mappings sync automatically. [ADAPT] Code Connect is worth it only once we're paying for Figma Organization/Enterprise seats anyway (e.g., once a design collaborator joins); until then, the DTCG-tokens-plus-copied-shadcn-components pipeline already recommended needs no Figma dependency at all — don't buy the seat upgrade for this alone.

**Component-library QA — Chromatic is the direct answer to the "own your code" risk this report itself flags.** **Chromatic** [storybook.js.org/docs/writing-tests/visual-testing], built by the Storybook maintainers, runs **visual regression testing per Storybook story**: first run establishes pixel baselines, every subsequent run diffs new snapshots against them, a human reviews only the flagged visual changes in a UI, and approved diffs become the new baseline — integrated as a CI/PR check (recent docs reference version 10.6 and a Vitest-addon integration for the testing widget). This is the direct mitigation for the specific risk this report already names as the cost of "own your code, copy-in components" (§1, recommendation #1): once shadcn components are copied into our repo, **nothing upstream will ever tell us if we've broken one** — no `npm audit`, no upstream changelog, nothing. Chromatic-on-Storybook is how teams catch that silently, per-component, on every PR, rather than discovering a broken date picker in production. [ADOPT] Storybook + Chromatic (or an equivalent open-source visual-diff tool if budget requires — Chromatic has a free tier for small snapshot volumes) as soon as the component library has ~10+ components — this is cheap insurance directly against the "own your code" recommendation's stated downside, not a nice-to-have.
