# Zero-training UX: onboarding, defaults, progressive disclosure

**TL;DR**
1. Tutorials and product tours consistently underperform — users skip them, forget steps taken out of context, and resent the interruption; the fix is contextual, in-flow help plus a home screen that is self-explanatory on first paint.
2. Templates and "teaching" empty states solve the blank-page problem better than any tour — Notion's growth engine is 30,000+ templates, not an onboarding wizard.
3. Power and simplicity are not opposites if you use progressive disclosure correctly: show 3–5 primary options by default, put everything else one deliberate click away, and never bury a feature most people need every day.
4. Undo beats confirm dialogs, optimistic UI beats spinners, and autosave beats a Save button — each removes a moment where the user has to think about the tool instead of the work; all three are justified by the same response-time research (0.1s/1s/10s thresholds).
5. For a Uzbek ministry: default to desktop-first (office PCs, not phones-in-pocket), Cyrillic-capable typography, plain-language Uzbek/Russian at roughly a 9th-grade reading level, WCAG 2.2 AA as the accessibility floor, and zero mandatory tours — the home screen and the empty states are the onboarding.

## 1. The core tension, and how the literature actually resolves it

Nielsen Norman Group's framing of **progressive disclosure** is the cleanest resolution of "Jira power without Jira's learning curve": show users only the most important options initially, and make a larger set of specialized options available on request — the two things that make this work are (a) correctly splitting features into "primary" vs "secondary," and (b) making the path to secondary options obvious through visible, well-labeled controls. NNGroup's own warning list is worth repeating verbatim because it names the two ways teams get this wrong: hiding a feature people need constantly, and stacking more than two levels of disclosure until users get lost. ([nngroup.com/articles/progressive-disclosure](https://www.nngroup.com/articles/progressive-disclosure/))

This is the design mandate for our platform: **one screen, ~5 numbers, plain labels** (the reference prototype's Overview already does this) as the permanent default, with power tools — bulk edit, custom fields, saved filters, automation rules — living one click away, never on the landing surface.

Nielsen's ten usability heuristics remain the checklist to audit every screen against before shipping. The two most load-bearing for a government tool with no training budget:

| Heuristic | What it demands of us |
|---|---|
| Match between system and the real world | Use the department's actual vocabulary — "sub-department," "weekly comment," "RSVP" — never generic SaaS nouns like "workspace" or "epic" |
| Recognition rather than recall | Never require a civil servant to remember a project code, a status taxonomy, or a keyboard shortcut they saw once — show it |
| Flexibility and efficiency of use | Keyboard shortcuts and shortcuts for experts must coexist with menu items for everyone else — this is literally the definition of progressive disclosure applied to input, not just display |
| Error prevention / recovery | Prefer disabling an invalid action over letting the user commit it, and always offer a plain-language recovery path |
| Help and documentation | Should be searchable and task-focused, not a manual — most of ours should live inside empty states and inline hints, not a separate "Help" section |

(Full list: [nngroup.com/articles/ten-usability-heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/))

Cognitive load research gives the mechanism behind "don't make me think": **intrinsic load** (the real complexity of the civil servant's actual task — is this project at risk, who owns it) is unavoidable and fine; **extraneous load** (parsing an unfamiliar icon, remembering which menu a setting lives under, re-entering a name the system already has) is pure waste and the thing to design out. NNGroup's three levers are directly usable as a design checklist: strip decorative/duplicate UI, reuse mental models the person already has from other software (native OS conventions, not novel ones), and offload work onto the system — autofill, smart defaults, pre-filled forms — rather than the person. ([nngroup.com/articles/minimize-cognitive-load](https://www.nngroup.com/articles/minimize-cognitive-load/))

## 2. Why product tours fail, and what actually replaces them

NNGroup's research on onboarding tutorials is blunt: tutorials fight the "paradox of the active user" — people want to act immediately, not sit through instruction, so they skip tours; and even when they don't skip them, information given out of context is hard to recall later because it was never tied to a real task, conflicting with how working memory functions. The interruption itself (a spotlight overlay blocking the screen mid-task) creates resentment rather than goodwill. ([nngroup.com/articles/onboarding-tutorials](https://www.nngroup.com/articles/onboarding-tutorials/))

The replacement pattern NNGroup recommends is **"pull revelations"** — contextual help that appears when the user is actually doing the thing (hover tooltips, coach marks tied to a specific control, wizards that trigger on first use of a feature) rather than **"push"** tutorials that front-load everything before any real task starts. Concretely this means: skip explaining obvious conventions (a gear icon does not need a tooltip), make every hint dismissible and recoverable later, and place the explanation directly beside the control it describes rather than in a separate panel.

Empty states are the single highest-leverage onboarding surface, because they appear exactly when the user needs to know what to do next and nowhere else. NNGroup's guidance: never leave a truly blank space (it reads as broken, not empty); state plainly what belongs there and why ("Star your favorites to list them here" is their cited example); and always pair the explanation with a direct action — a "Create" button, not just a "Learn more" link. ([nngroup.com/articles/empty-state-interface-design](https://www.nngroup.com/articles/empty-state-interface-design/)) For us this means: an empty Projects register should say "No projects yet in Strategy & Rankings — add the EGDI 2026 audit to get started" with a one-click create, not a generic "No data."

**Templates are the real onboarding mechanism**, and Notion is the clearest evidence: its template gallery (30,000+ templates, browsable by category and use case) exists specifically to remove the blank-canvas problem — a new user never designs a system from nothing, they adapt something that already works. ([notion.com/templates](https://www.notion.com/templates)) For a government tool this is directly portable: every module (a project, a weekly report, an activity plan) should ship with 2–3 named templates pre-loaded with the department's own real structure (e.g., "EGDI ranking project" template with the fields Strategy & Rankings actually uses), not an empty form.

## 3. Keyboard-first, without excluding anyone

**cmdk** (MIT license, github.com/pacocoursey/cmdk) is the open-source React primitive behind the Linear/Vercel/Raycast-style command palette: an unstyled, accessible combobox component (`Command`, `Command.Input`, `Command.List`, `Command.Item`, `Command.Group`, `Command.Dialog`) with built-in fuzzy filtering, nested "pages" for hierarchical menus, async item loading, and full keyboard navigation/ARIA support — it was originally built for the Vercel command menu. React 18+ required. ([github.com/pacocoursey/cmdk](https://github.com/pacocoursey/cmdk)) This is a safe, cheap, well-trodden choice for our stack: Ctrl/Cmd+K opens a palette that can create a project, jump to a person, or run "go to Data & BI Analytics" without touching a menu.

The pattern that makes command palettes learnable without training is that **they never replace the visible UI** — every action reachable by Ctrl+K must also be reachable by clicking, so nobody is ever stuck. This is progressive disclosure applied to *input method* rather than screen layout: novices click, experts type, both reach the same place.

**Natural-language quick-add** (Todoist's classic pattern: typing "Submit EGDI draft every Friday 5pm #StrategyRankings p1" auto-parses date, recurrence, project, and priority from one line; Things and Amie use similar magic-parsing for quick entry) removes the multi-field-form tax for the single most frequent action in any work tool — capturing a new task. For a civil-service audience this argues for a single quick-add box, parsed in Uzbek/Russian/English, that understands relative dates ("ertaga," "завтра," "tomorrow") and department names, rather than a modal with eight required fields.

**Search-as-navigation** (typing a person's name, a project title, or a status word and landing directly on the record, the way Slack/Linear/Notion all default Ctrl+K to search-first) should be the primary way to move around the tool, because it means the information architecture never has to be perfectly guessed by a new user — they don't need to know which of five menus a project lives under if they can just type its name.

## 4. Trust the system: undo, optimistic UI, autosave

Response-time research underlies three separate patterns that all reduce to the same idea — never make the user wait to find out if their action worked. The classic thresholds (roughly: under ~0.1s feels instantaneous, up to ~1s keeps the user's flow of thought uninterrupted, and beyond ~10s the user's attention leaves the task) are the reason **optimistic UI** exists: update the screen immediately, assuming success, and reconcile quietly in the background rather than showing a spinner and making the user wait for a round trip before they see the result of their own click.

The same logic argues for **undo over confirm dialogs**: a confirmation ("Are you sure you want to delete this?") interrupts every single action to guard against a rare mistake, punishing 99 out of 100 correct actions to catch the 1 wrong one; undo lets the action complete immediately (fast, trusts the user) and offers a brief, cheap way to reverse it if it was wrong. This is the reasoning behind Gmail's "Undo Send" and most modern delete flows (toast notification with an Undo button rather than a modal). Nielsen's own heuristic #3, "user control and freedom," names this directly: interfaces need a clearly marked emergency exit, ideally undo, not a gate before the action.

**Autosave** is the same principle applied to data entry: removing the "Save" button removes a decision point and a place to lose work, and it matches how every tool a civil servant already trusts (Google Docs, Word 365, a phone's Notes app) already behaves — this is "match between system and the real world" again, not a new pattern to learn.

## 5. Mobile vs. desktop for office workers

NNGroup's position, directly relevant here, is that **"mobile-first" is a design-thinking discipline, not a mandate to make desktop look like mobile** — porting mobile patterns (hamburger menus, hidden nav, icon-only search) onto a large screen historically produces worse desktop experiences, echoing every past platform-porting failure (DOS→Windows, print→web). Desktop deserves its own optimization: visible navigation, real search boxes, layouts that use the space a cursor and a big screen actually afford. ([nngroup.com/articles/mobile-first-not-mobile-only](https://www.nngroup.com/articles/mobile-first-not-mobile-only/))

For our specific users — ministry staff at desks, on department-issued Windows PCs, for 8 hours a day — this settles the debate: **design desktop-first**, and treat mobile as a companion surface (checking a KPI, RSVP'ing to an event, approving something from Telegram) rather than the primary work surface. This also matches how Telegram fits in: not as the app itself, but as a notification/quick-action channel into a desktop-first tool — a bot that can post "3 projects need your weekly comment" and let a one-tap reply update status, without requiring the desktop app to be mobile-native.

## 6. Accessibility and low digital literacy

WCAG 2.2 (a W3C Recommendation — first published 5 October 2023, and now current at **12 December 2024**: the live specification at [w3.org/TR/WCAG22/](https://www.w3.org/TR/WCAG22/) is a republished/corrected Recommendation carrying that later date, confirmed by direct fetch of the live document this session — and the up-to-date baseline through 2025–2026) adds several AA criteria directly relevant to a government tool used by staff of every age and ability, most notably **2.5.8 Target Size (Minimum)**: pointer targets must be at least 24×24 CSS pixels, with defined exceptions for inline links, equivalent alternative controls, spacing-based passes, and legally mandated layouts. ([w3.org/WAI/WCAG22/Understanding/target-size-minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)) Practically: no icon-only button smaller than ~24px, ever, anywhere a civil servant with reduced fine motor control might click — this rules out cramped icon toolbars as a primary interaction surface and reinforces text-labeled buttons as the default.

Other 2.2 AA additions worth designing to from day one: **2.4.11 Focus Not Obscured** (a sticky header must never cover the keyboard-focused element), **2.4.12 Focus Appearance** (visible, high-contrast focus rings — critical for keyboard-only users and anyone relying on Windows High Contrast mode), **2.5.7 Dragging Movements** (any drag-to-reorder, e.g. Kanban cards, needs a non-drag alternative — click-to-move), and **1.4.13 Content on Hover or Focus** (tooltips must be dismissible and not disappear before they can be read).

"Low digital literacy" and "older user" design (a real population here — sub-department heads and the Director are unlikely to be power users of SaaS tools) converges on the same rules as zero-training UX generally: large, obvious, text-labeled controls; one clear primary action per screen; no jargon; no modal stacking; and forgiving interactions (undo, confirmation only for truly destructive/irreversible actions, autosave). This is not a separate design system from "good UX for everyone" — it is the same system with less tolerance for cleverness.

## 7. UX writing and Uzbek/Russian localization

GOV.UK's content design discipline is the best public reference for plain-language government writing: the standard is short sentences, one idea per sentence, active voice, addressing the reader as "you," and a house style guide banning bureaucratic jargon — the practice exists specifically because government services must be understandable to every citizen regardless of education level, the same requirement a multi-tenant Uzbek gov tool has by law and by the "zero training" brief. GOV.UK also formalizes these rules as reusable **design patterns** (task lists, notification banners, question-per-page forms) rather than one-off screens, which is directly reusable as an approach: build our own small pattern library (status chip, weekly-comment card, RSVP tile) once, and reuse it everywhere so a person only has to learn each pattern once. ([gov.uk/service-manual/design](https://www.gov.uk/service-manual/design))

Localization specifics for Uzbek/Russian (practitioner knowledge — flagged in Open Questions as needing native-speaker/linguist verification, since live search access was unavailable this session):
- **Two scripts, three languages.** Uzbek has an incomplete Latin-script transition — Cyrillic Uzbek and Russian remain in everyday government use, especially among staff over ~40. A UI that only ships Latin-script Uzbek will alienate part of the actual user base; Cyrillic Uzbek should be budgeted as a fourth locale, not assumed to be covered by "Russian."
- **Text expansion.** Russian and Uzbek strings typically run 20–35% longer than the English equivalent for the same meaning — button labels, status chips, and nav items need width budgets planned for this rather than fixed to English-length strings.
- **Register mismatch risk.** Plain-language, second-person, friendly tone (the GOV.UK style) can read as disrespectful in formal Russian/Uzbek bureaucratic correspondence, where formal address and title use is the norm; copy needs a government-appropriate plain style, not a literal transplant of GOV.UK's informal voice — this is a genuine open design tension, not a solved problem.
- **Fonts.** Any chosen typeface must have full, well-hinted Cyrillic glyph coverage (Inter, Golos Text, and Noto Sans all qualify) — many trendy Latin-only display fonts silently fall back to a system font for Cyrillic, breaking the visual identity for a large share of users.
- **Dates/numbers.** DD.MM.YYYY format, comma as decimal separator — deviating from local convention is exactly the kind of extraneous cognitive load Section 1 warns against.

## 9. First 10 minutes — a new civil servant (first login, no training)

0:00 – Login via SSO/Telegram-linked account (no password to remember). Land directly on **Overview**, in the department's default language (detected from OS locale, switchable top-right).
0:30 – Overview shows 4–5 numbers max (echoing the reference prototype's KPI cards): headcount, active projects, portfolio health, this quarter's priorities. No modal, no tour — the screen is the explanation.
1:30 – A single, dismissible banner: "New here? Here's your team" with one button → **People**, pre-filtered to the person's own sub-department.
2:30 – On People, an empty "About you" card at the top nudges: "Add your photo and phone number — only your manager can see personal details" (this is a "teaching" empty state, not a form dump).
4:00 – Person clicks their sub-department in the org chart → sees the unit's mandate paragraph, teammates, and active projects — answering "who am I working with and on what" without being told to look anywhere.
6:00 – Person opens **Projects**, sees only what's assigned to them (view defaults to "mine," not "all"), each with a status chip and a single line: "leads add one short comment every Friday" — the operating ritual is explained inline on the screen where it applies, not in a manual.
8:00 – Person tries the quick-add box (always visible, top of screen): types "Draft FinTech briefing Friday" — it parses a due date automatically; no modal, no required fields beyond a title.
10:00 – Done. The person has seen their team, their work, and made one real edit — with zero screens dedicated to "welcome" or "let us show you around."

## 10. First 10 minutes — a department head

0:00 – Lands on **Overview** but scoped to their sub-department by default, with a one-click toggle to see the whole department (role-aware default view, not a setting they must find).
1:00 – Sees their team's headcount, active project count, and — critically — the **escalation queue**: any project that missed its Friday comment or is blocked, surfaced automatically per the reference prototype's auto-escalation rule, with no need to dig through a table.
3:00 – Clicks into one escalated project; sees the comment history and status changes as a timeline, and can leave a comment or reassign directly from that view — no separate "admin" screen required.
5:00 – Opens **People** for their unit, sees each teammate's current workload (a Phase-3 idea, but even a simple "active project count per person" column works on day one) so a first meeting can be about real distribution of work, not guessing.
7:00 – Checks the quarterly priorities' progress bars, mirrors the reference prototype's "Department priorities" section — a talking point ready-made for their next check-in with the Director.
9:00 – Tries the command palette (Ctrl+K), types a teammate's name, jumps straight to their profile — the head experiences the power-user path exists, without ever needing it explained.
10:00 – Done. No settings screen, no "invite your team" step forced up front (that can be a background admin task, not day-one friction) — the head has already seen the one thing they came for: is my unit on track.

## 11. What this means for us

1. **[ADOPT]** Progressive disclosure as the literal screen-design rule: 3–5 primary items visible by default, everything else exactly one click away, never three levels deep — matches NNGroup's explicit failure mode of "too many disclosure levels." (nngroup.com/articles/progressive-disclosure)
2. **[ADOPT]** Kill the product tour entirely; replace every "Welcome, let's show you around" step with a teaching empty state placed exactly where the relevant action happens — tours are proven to underperform against contextual, in-flow help. (nngroup.com/articles/onboarding-tutorials)
3. **[ADOPT]** Ship named, department-specific templates for every object type (a project, a weekly report, an activity plan) pre-filled with real department vocabulary — this is Notion's actual onboarding mechanism, not its database flexibility. (notion.com/templates)
4. **[ADOPT]** cmdk (MIT) for a Ctrl/Cmd+K command palette, but require every action it exposes to also exist as a clickable control — command palettes must never become the only path, or they exclude the very users we're building for. (github.com/pacocoursey/cmdk)
5. **[ADOPT]** Undo-first destructive actions (toast + Undo) instead of confirmation modals for anything recoverable (archiving a project, removing a comment); reserve true confirm dialogs for genuinely irreversible acts (deleting a person's record) — matches Nielsen's "user control and freedom" heuristic.
6. **[ADOPT]** Autosave everywhere, with a small, honest "Saved" indicator — never a Save button — to match the response-time expectations users already carry from Docs/Word.
7. **[ADOPT]** A single natural-language quick-add box, localized to parse Uzbek/Russian/English relative dates and department names, as the default way to create work — reduces the "form with 8 required fields" tax that kills first-use activation.
8. **[ADOPT]** Desktop-first layout for the core app; mobile/Telegram as a companion notification and quick-action surface only — matches both NNGroup's mobile-vs-desktop research and the reality of office PCs as the daily tool. (nngroup.com/articles/mobile-first-not-mobile-only)
9. **[ADOPT]** WCAG 2.2 AA as a hard floor from the first commit, not a later pass — specifically 24×24px minimum targets and visible keyboard focus, both cheap to build in and expensive to retrofit. (w3.org/WAI/WCAG22/Understanding/target-size-minimum)
10. **[ADAPT]** GOV.UK's plain-language writing discipline (short sentences, active voice, one idea per sentence, banned jargon list) — adopt the method, but soften the informal "you" tone toward a register appropriate to formal Uzbek/Russian government correspondence; this needs native-speaker review, not a literal port. (gov.uk/service-manual/design)
11. **[ADAPT]** Superhuman's obsession with a single activation metric — the Sean Ellis "40% very disappointed" bar, against which Superhuman tracked its own climb from 22% → 33% → 58% by segmenting responses and rebuilding the roadmap around them — adapt to something like "% of leads who post their Friday comment without a reminder" as our own home-grown PMF proxy, run with the same discipline (survey quarterly, segment the "disappointed" answers, act on them), since the white-glove onboarding call itself (a detail from secondary sources, not the First Round Review article) doesn't scale to a ministry. (review.firstround.com/how-superhuman-built-an-engine-to-find-product-market-fit)
12. **[ADAPT]** Linear's opinionated, keyboard-first defaults — adopt the "one right way to do it" philosophy for status taxonomies and workflows, but keep every keyboard path mirrored by a mouse path, since our audience did not choose to be power users the way Linear's did.
13. **[AVOID]** Mandatory onboarding wizards or multi-step "set up your workspace" flows before any real value is shown — every source here (NNGroup on tutorials, Notion's template-first model, our own "first 10 minutes" designs above) argues the home screen and real data should appear immediately, with setup happening in the background or as an admin task, not gating day one.
14. **[AVOID]** Icon-only, sub-24px toolbars as a primary interaction surface — fails WCAG 2.2 target-size and fails "recognition over recall" for a low-training audience; always pair icons with visible text labels for primary actions.
15. **[AVOID]** Treating Uzbek as a single locale — Cyrillic Uzbek and Russian are not "the same as Latin Uzbek with different letters" in practice; skipping Cyrillic Uzbek risks excluding older/rural-origin staff exactly like an unlabeled icon toolbar would.

### 1. The "feature-rich but not overwhelming" method

The original report stated the *principle* (progressive disclosure, 3–5 items visible, everything else one click away) without a concrete method a designer could apply screen-by-screen. NNGroup's own progressive-disclosure article, re-checked directly this session, is explicit that it deliberately gives no numeric rule — "initially, show users only a few of the most important options," with the actual split determined by task analysis and usage-frequency data, not a formula. ([nngroup.com/articles/progressive-disclosure](https://www.nngroup.com/articles/progressive-disclosure/)) So the numbers below are *our* design rule, informed by that method, not a claim that NNGroup mandates them.

**Information architecture — 5 top-level areas, no exceptions.** General enterprise-IA guidance converges on keeping primary navigation to roughly 2–7 items, and names the specific failure mode to avoid: giving every new feature its own top-level nav slot, which typically degrades into an unmanaged 20–30-item sidebar within a couple of years. For WorkPortal, the five permanent top-level areas are:

| # | Area | Contains |
|---|---|---|
| 1 | **Overview** | Role-scoped home: 4–5 numbers, escalations, priorities (Sections 9–10 above) |
| 2 | **Work** | Projects, tasks, boards — the Jira-power area |
| 3 | **People** | Org chart, profiles, and (as a tab, not a 6th nav item) the newcomer onboarding module — see Section 2 below |
| 4 | **Requests** | Approvals, tickets, sign-offs |
| 5 | **Events** | Calendar, RSVPs, team building |

AI assistance is deliberately **not** a nav destination — it lives inside the command palette and as an inline "Ask" affordance on records, the same way Notion's Cmd+K also answers questions rather than routing to a separate "AI" tab (see Section 6 below). Newcomer onboarding is likewise not a permanent nav item: it is a self-removing checklist surfaced inside Overview and People for exactly as long as it's relevant (see Section 2 below), which is itself the answer to "how do you fit onboarding into a 5-item IA without cluttering the nav for the other 22 people who already work here."

**Three explicit disclosure tiers**, applied to every screen, not just the home screen:
- **Tier 0 — default (zero clicks):** what's visible on first paint — 3–5 cards/numbers/primary actions (Section 1's existing rule).
- **Tier 1 — one click:** an overflow ("…") menu, a settings drawer, "show all fields," bulk actions that appear once rows are selected — always behind a *visible, labeled* control, never a hidden gesture, per NNGroup's own warning against undiscoverable secondary features.
- **Tier 2 — power:** command-palette actions, keyboard shortcuts, custom fields, saved filters, automation rules, admin/config screens — reached by search (Ctrl/Cmd+K) or a clearly labeled "Advanced" section, never required to complete the Tier-0 task.

**Density modes.** A per-user, remembered "Comfortable / Compact" toggle — comfortable (larger row height, more whitespace) as the default for the low-digital-literacy and older-user population Section 6 identifies, compact (more rows per screen) as an opt-in for power users who process long lists daily (a department head's escalation queue, an HR admin's request queue). This is the same pattern Linear/Notion/Airtable-class tools all ship: core features stay always visible while a single-interaction toggle like this serves a specific, self-selected use case without permanently changing the interface for everyone else.

**Personal "show me more" unlocking.** A per-user, reversible toggle (in the profile, not an admin-granted permission) that reveals Tier-2 controls inline — bulk edit, custom fields, the automation panel — once a person actually wants them. It can be self-discovered (an always-visible but unobtrusive "Show more tools" link) or gently suggested after real usage (e.g., after creating ten tasks: a dismissible hint, "Want to bulk-edit these? Turn on more tools in your profile"). This borrows two ideas directly from the research: Raycast's split between a lean built-in core and an opt-in extension catalogue that power users grow into over time, and Airtable's onboarding-personalization finding that showing role-relevant advanced options (not all advanced options) reportedly helped activation without overwhelming the default flow ([raycast.com](https://www.raycast.com/); the Airtable/Reforge claim could not be re-fetched this session — HTTP 403 — so it rests on the WebSearch summary of it, not a direct read, and should be treated as secondary until re-verified: [reforge.com/artifacts/onboarding-experiment-result-personalization-airtable](https://www.reforge.com/artifacts/onboarding-experiment-result-personalization-airtable)).

**Role-based defaults**, extended beyond the two personas the original report designed for:

| Role | Default landing scope | Default filter |
|---|---|---|
| Specialist | Overview, own sub-department | "Mine" |
| Head | Overview, own sub-department, one-click toggle to whole department | "My unit" |
| Director | Overview, whole department, no toggle needed | "Whole department" + director-level escalations only |
| HR/Admin | A People-operations queue (newcomers, access requests, overdue checklists), not the generic Overview | "Needs action" |

Each row is a config value, not a hand-built screen — the same screen renders differently based on one "default scope" and one "default filter" setting per role.

### 2. The newcomer onboarding module

**What the commercial templates actually contain**, verified this session:
- **Rippling's** checklist splits into pre-boarding (before day 1: welcome email, policy access, payroll forms, equipment ordered, buddy assigned — owned by HR/IT), day one (a roster "cheat sheet" of names/titles/contacts, owned by HR/manager), first week (org-wide training on goals/purpose/values, then role-specific training, owned by the manager with buddy support), and first 90 days (weekly 1:1s, 30/60/90-day feedback, owned by the manager). ([rippling.com/blog/free-onboarding-checklist](https://www.rippling.com/blog/free-onboarding-checklist))
- **Donut's** "Journeys" product automates exactly the multi-owner problem the original report never addressed: it "sends scheduled messages and polls, makes introductions, and assigns tasks to your new hires, managers, and anyone else involved," with managers getting their own reminders (pre-boarding prep, 30/60/90 check-ins) and an admin dashboard that tracks every new hire's completion status without manual follow-up. ([help.donut.ai/en/articles/657523-donut-journeys-onboarding](https://help.donut.ai/en/articles/657523-donut-journeys-onboarding))
- **Trello's** onboarding templates are checklist-and-card based ("New Hire Onboarding," "30-60-90 Day Plan," each emphasizing "clear goals and checklists of to-do's") and point toward a dedicated card for pairing the new hire with a buddy — a lighter, visual version of the same idea. ([trello.com/use-cases/onboarding](https://trello.com/use-cases/onboarding))
- **Notion's** contribution (already covered in the original report for templates generally) is the same principle applied here: an onboarding *page*, not a form — a pre-built checklist page the newcomer reads top to bottom, with embedded links to the reading list and org chart, rather than a wizard.

**The concrete UI mechanism: GOV.UK's "complete multiple tasks" pattern**, fetched directly this session, is the exact middle option the editor's note said was missing between a blocking tour and a passive empty state. Its rules, quoted directly, map onto our checklist almost without modification:
- Statuses: **Completed** (plain text, no background), **In progress** (tag), **Not yet started** (tag), **Cannot start yet** (greyed out, for genuine dependencies — e.g., "Set up your account" is greyed out until HR has provisioned access), and a red "There is a problem" tag reserved *only* for actual errors, never for an unstarted task.
- "Start with the smallest number of different statuses you think might work... then add more if your user research shows there's a need for them" — for us, ship with Completed / Not started / Cannot start yet and add "In progress" only if a newcomer's own usage shows they need to mark partial progress.
- Users self-declare completion; they can always go back into a finished task to change their answer.
- "Try to simplify the transaction before you use a complete multiple tasks page" — the checklist is for genuinely multi-session, multi-owner work (which onboarding is); it is not the answer for anything that fits on one screen. ([design-system.service.gov.uk/patterns/complete-multiple-tasks](https://design-system.service.gov.uk/patterns/complete-multiple-tasks/))

This also answers the editor's broader "checklists as a middle option" gap: the same task-list component is the right pattern for *any* multi-session, multi-owner setup in the product (a new project's initial configuration, a new sub-department's first quarter), not only HR onboarding — it should be built once, as a shared component, and reused (ties directly into the design-system-governance gap in Section 8 below).

**Four parallel, linked checklists, not one.** The single biggest gap in the original report was never asking *who* does the onboarding tasks — Donut's model above shows the answer is never just the newcomer. WorkPortal's onboarding record for a new hire generates four linked checklists against one shared record:

| Checklist owner | Example tasks |
|---|---|
| **HR/Admin** | Order equipment, provision system access, generate accounts, confirm contract paperwork |
| **Manager (head)** | Assign a buddy if not yet assigned, confirm the sub-department's mandate paragraph is current, schedule a Day-1 welcome and a Week-1 check-in |
| **Buddy** | Send an informal welcome message, meet in person/coffee in week one, be the "questions you don't ask your manager" contact (a role named explicitly across the 30-60-90 sources) |
| **Newcomer** | Complete the "About you" card, read the department mandate and 2–3 named reading-list items, meet the org chart, make one real edit (Section 9's "first 10 minutes") |

**Auto-generation.** Entering a hire's start date and sub-department is the only manual step: it instantiates all four checklists from a role + sub-department template, auto-creates Day-1/Week-1 meeting placeholders on the manager's and buddy's calendars, and — if no buddy is set — prompts the head with a one-click "assign a buddy" nudge rather than silently leaving the task undone.

**Progress visibility.** A single shared progress view (not four separate screens) shows all four checklists' status side by side, visible to HR and the manager — mirroring Donut's admin-dashboard pattern of tracking every new hire's status "without requiring manual follow-ups." For a 23-person department this view realistically shows 0–3 active onboardings at a time, so it can be a simple list, not a dashboard with charts.

### 4. Contextual help that replaces tours

Steve Krug's "Don't Make Me Think," explicitly named in the brief and never cited in the original report, gives the exact hierarchy the report's ethos was already gesturing at without naming it: **"aim for self-evident first; if that fails, self-explanatory is second-best; try not to need to explain at all."** His navigation test (a page should instantly answer "what is this, where am I, where can I go") and his "Third Law" — get rid of half the words, then half of what's left, cutting "happy talk" and unread instructions first — are both directly actionable rules, not just an ethos. ([sive.rs/book/DontMakeMeThink](https://sive.rs/book/DontMakeMeThink))

Applied concretely, our contextual-help stack has three layers, none of which is a tour:
1. **Inline examples as placeholder text**, not a separate instruction — the quick-add box's placeholder is a real example, not "Enter a task": EN "e.g. Draft FinTech briefing Friday" / UZ "Masalan: FinTech bo'yicha ma'lumotnomani jumagacha tayyorlash" / RU "Например: подготовить справку по FinTech к пятнице" (Section 3's quick-add, now with the actual copy).
2. **A "?" affordance on every screen** that opens a short, task-scoped panel (2–4 sentences plus one example), not a searchable help center — this is GOV.UK's own "help users to..." pattern family (start using a service, check answers, recover from errors) applied per-screen instead of as a site-wide manual.
3. **Hover hints on anything genuinely non-obvious** (an icon, a status color's meaning) — but per Krug and Section 1's cognitive-load argument, a hint is a sign a control failed the "self-evident" test, so hints are a last resort, not the default help mechanism, and every hint must be dismissible and re-appear on demand (WCAG 1.4.13, already cited in Section 6).

**Product tours fail for more reasons than the original report covered.** Beyond the paradox-of-the-active-user and working-memory mismatch already cited, the practitioner literature adds a maintenance argument that matters for a small engineering team building a government tool: tours built against hard-coded UI selectors break on every UI change, and if updating a tour requires a developer every time the UI changes, teams stop updating them — an unmaintained tour becomes actively worse than no tour, since it now shows wrong information confidently. Tours also don't adapt by role (a director and a specialist land on the same generic tour) and resent replay on returning users rather than offering a shortcut or refresher. Our contextual-help stack above sidesteps all three failure modes because it's tied to the control it explains, not a scripted sequence, so it can't "break" the same way and never needs to know who's already seen it.

**What screen readers need that the original WCAG section missed.** ARIA live regions (`aria-live="polite"` for routine updates, `"assertive"` reserved for genuinely urgent interruptions) are how a screen reader learns that a toast appeared at all — but live-region announcements are transient: once spoken, they cannot be reviewed, which is a real problem for exactly the Undo-toast pattern Section 4 recommends everywhere. The fix: pair the polite live-region announcement with a **persistent, keyboard-focusable toast element** in the DOM (not the announcement alone), so a screen-reader or keyboard user who wasn't listening at the exact moment can still tab to the toast and activate Undo. ([sarasoueidan.com/blog/accessible-notifications-with-aria-live-regions-part-1](https://www.sarasoueidan.com/blog/accessible-notifications-with-aria-live-regions-part-1/)) Beyond toasts, every screen needs standard landmark regions (`nav`, `main`, `search`) and a real heading hierarchy so a screen-reader user can jump structure-first the way a sighted user scans visually — cheap to build in from the first component, expensive to retrofit, the same argument Section 6 already makes for target size.

**Resolving the orphaned Error Message Guidelines citation:** the Sources list already links NNGroup's error-message article but the body never used it. Applied here: every validation error should state what went wrong in plain language, say how to fix it, and appear next to the field it concerns (not in a summary banner alone) — directly reusable for our multilingual forms, and worth an explicit line so the citation isn't dead weight.

### 5. Keyboard shortcut discoverability

The original report described Ctrl+K well but never addressed how a first-time user finds out shortcuts exist at all. Three concrete, converging patterns from the research:
- **A "?" overlay**, the long-standing convention across Google's web apps and Superhuman alike (press `?` or `Cmd+?` for a full shortcut list) — cheap to build, and consistent with the existing Ctrl+K mental model (a second, equally simple key to remember).
- **Shortcut hints shown in place**, not only in a separate cheat sheet — every menu item and tooltip that has a shortcut shows it next to the label (e.g., a "Create task" button shows "C" beside it), which is "recognition rather than recall" (Section 1's own heuristic table) applied to shortcuts specifically, not just to visible UI.
- **Context-aware overlays**, the pattern Microsoft's PowerToys Shortcut Guide popularized for Windows generally: the overlay "detects the active program and displays relevant keyboard commands for that software," replacing recall with recognition and solving the exact problem practitioners flag — someone who discovered a shortcut and used it once or twice is very likely to forget it by the next session. ([xda-developers.com/powertoys-shortcut-guide](https://www.xda-developers.com/powertoys-shortcut-guide-makes-quick-navigation-easier-than-ever-and-its-another-feature-windows-should-have-shipped/)) For us this argues for a "?" overlay that is itself context-aware — showing shortcuts relevant to the current screen first, not one undifferentiated global list.
- **A first-use toast**, shown once, the first time a person completes an action that has a shortcut equivalent ("Tip: press C to create a task next time"), dismissible and never repeated — the "pull revelation" pattern from Section 2 of the original report, applied specifically to shortcuts.

### 6. Surfacing many features without clutter: what Linear, Superhuman, Raycast, and Things 3 actually do differently

The original report treated Linear/Raycast/Notion as an undifferentiated "keyboard-first" reference; the research shows genuinely different mechanisms worth naming separately, since our cmdk implementation (Section 3 of the original report) should borrow deliberately from each:
- **Linear** bakes single-keystroke creation into the palette itself (a bare "C" creates an issue from anywhere) rather than requiring "open palette → type create → select" — a shortcut for the single most frequent action, layered on top of the general search-first palette.
- **Raycast** is a system-level launcher (`Cmd+Space`), not an in-app palette, with a separate in-context **Action Panel** (`Cmd/Ctrl+K`) for secondary actions once something is already selected — a two-tier structure (global launch vs. contextual actions) rather than one flat list.
- **Notion's** Cmd+K doubles as an AI question box, not only a navigation/search tool — the precedent our IA decision above (Section 1) already leans on for keeping AI assistance out of the nav bar.
- **Superhuman's** own well-documented practice (beyond the PMF metric already covered) is to teach its keyboard-first model through a dedicated, guided education moment rather than assuming discovery — the exact thing that doesn't scale to a ministry (Section 8's verdict already says skip the white-glove call). The scalable substitute is the first-use toast and context-aware "?" overlay from Section 5 above: a **compressed, self-serve version of the same idea** — teach 2–3 shortcuts in the moment they're useful, not all of them in one mandatory sitting.
- **Raycast's extension model** (a lean built-in core plus an opt-in catalogue power users grow into) and the general progressive-disclosure finding that interfaces deferring advanced features to a secondary layer speed up first-task completion while preserving full discoverability are the direct precedent for Section 1's "show me more" toggle above — Things 3 belongs in the same family (a task manager praised specifically for looking simple by default while still supporting tags, projects, and areas for anyone who wants them), though no single citable source analyzes *why* Things 3 in particular succeeds at this beyond the general progressive-disclosure literature already cited — that specific gap (a dedicated Things 3 case study) remains open and should be a targeted follow-up if the design team wants primary evidence rather than an inference from the general pattern.

### 7. Metrics: measuring adoption in a 23-person department

Standard SaaS adoption metrics assume enough users that percentages are stable; at 23 people, **each person is worth about 4.3 percentage points** — a single person's behavior can swing "adoption rate" by more than most SaaS benchmarks move in a quarter. The instrumentation plan below adapts the standard framework to that reality rather than importing it uncritically.

The general framework, confirmed this session, has four legs: **task success** (completion rates, error rates, time-to-completion for real workflows, not just logins), **engagement** (which features actually get used, not just who opened the app), **retention** (usage 30–90 days after go-live is the critical window — early drop-off signals the rollout didn't produce durable capability), and the **access-vs-value gap** — a login is not adoption; genuine adoption probably requires regular, real use to justify the cost, and organizations that measure only access systematically overstate how well a rollout is going. Pairing usage data with a short satisfaction survey (a practice Microsoft recommends for its own tools) closes the gap between "people are logged in" and "people find this worth using." ([userlane.com/blog/what-software-adoption-metrics-actually-measure](https://www.userlane.com/blog/what-software-adoption-metrics-actually-measure))

For our 23-person department, concretely:
- **Instrument the "first 10 minutes" flows directly** — the original report's most concrete deliverable (Sections 9–10, and the two new flows above) was never connected to a measurement plan, exactly as the editor flagged. Each numbered step in those flows is a loggable event; the funnel is "logged in → viewed Overview → clicked into People/a project → made one real edit," and drop-off between any two steps for any specific named person is the whole diagnostic at this scale (not a percentage, a name).
- **Track named completion, not cohort percentages**, for anything with fewer than ~30 people in the denominator (a sub-department's checklist completion, a specific onboarding cohort) — a simple list of who has/hasn't done the thing is more actionable than "78% completion" when 78% means 18 of 23 people.
- **Time-to-first-value as a defined event, not a vibe.** TTV is the elapsed time from first login to the "aha moment" — the point the person subjectively recognizes the tool is worth using, which for us is plausibly "the first time a person's own Friday comment or task shows up back to them as something someone else acted on." Define that event explicitly and time it per new hire, the same way Section 9's "first 10 minutes" narrative already implies but never states as a measurable target. ([digital-power.com — aha-moment framing](https://digital-power.com/en/inspiration/from-aha-moment-to-activated-users/))
- **The adapted Superhuman metric (verdict 11, corrected above)** is the department-wide health check: run the "would you be very disappointed" survey quarterly, segment the answers by role (specialist/head/director/HR), and act on what the "disappointed" group specifically says is missing — exactly the loop that took Superhuman from 22% to 58%, at a cadence and scale that fits 23 people.
- **A lightweight HEART-lite scorecard** (Happiness via the quarterly survey above, Engagement via named feature usage, Adoption via the onboarding-checklist completion list, Retention via 30/60/90-day check-ins already in Section 2's newcomer module, Task success via completion/error rates on real workflows) gives leadership one page to look at without building a BI dashboard nobody asked for.

### 8. Other named gaps closed

**Onboarding checklists, verdict:** ADOPT, generalized beyond HR — the GOV.UK task-list pattern in Section 2 above is the reusable component; it is the deliberate middle option between a blocking tour (killed, correctly, in the original report) and a passive empty state (the original report's only other tool), and it should back any genuinely multi-session, multi-owner setup, not just new-hire onboarding.

**Inbox-zero triage, applied to the escalation/Friday-comment queue.** The "5 D's" pattern (Delete/Delegate/Respond/Defer/Do), and the more general rule of separating *deciding* from *doing* by triaging in a fast, no-second-guessing pass, maps directly onto a head's or director's escalation queue: each item should resolve in one keystroke to one of a small fixed set of outcomes (comment now, reassign/delegate, snooze to next Friday, dismiss) rather than opening a full record every time — single-key triage on a queue no different in shape from an inbox. ([rock.so/blog/inbox-zero](https://www.rock.so/blog/inbox-zero))

**Notification volume and digest design.** Per-category cadence (real-time / daily digest / weekly digest), decided by the user, is the standard the research converges on, with a hard rule that anything genuinely time-sensitive (a direct @mention, a person's own escalation) always bypasses batching regardless of the user's digest preference. A Monday-morning digest — "here's what needs you this week" — is the scheduled-digest half of this pattern, and is the natural home for the "Director's briefing" card in Section 3 above and for the Telegram channel the original report already proposed as a companion surface. ([suprsend.com/post/notification-batching-and-digest](https://www.suprsend.com/post/notification-batching-and-digest))

| Donut (Slack app) | Multi-owner onboarding automation — tasks assigned to newcomer, manager, and buddy simultaneously, with a single admin progress view ([help.donut.ai](https://help.donut.ai/en/articles/657523-donut-journeys-onboarding)) | Built entirely inside Slack — we need the equivalent inside our own product, not a Slack-app dependency |

| Airtable | Personalizing onboarding examples/templates by the user's stated role or use case, reportedly improving activation ([reforge.com](https://www.reforge.com/artifacts/onboarding-experiment-result-personalization-airtable) — claim not re-verified this session, fetch blocked; treat as secondary) | A wizard-driven signup flow before any real data appears — contradicts this report's own "kill mandatory setup wizards" verdict (item 13) |
| Duolingo | Reduce friction and lower difficulty for returning/lapsed users; auto-filter notifications to respect attention ([growth.design/case-studies/duolingo-user-retention](https://www.growth.design/case-studies/duolingo-user-retention)) | Streaks, badges, leaderboards, loss-aversion mechanics — inappropriate gamification for mandatory government work software (see verdict 24 below) |

**i18n engineering trap: plural rules.** Russian requires **four** CLDR plural categories — `one`, `few`, `many`, `other` (e.g., 1 project / 2–4 projects / 5–20 projects / 21, 22–24... repeating) — not the two categories (`one`/`other`) that naive `{count} item(s)` interpolation assumes; shipping only `one`/`other` for Russian silently falls back and reads wrong to native speakers. ([locize.com/blog/i18n-pluralization](https://www.locize.com/blog/i18n-pluralization)) Uzbek's plural-category count under CLDR was not found in any source fetched this session — Turkic languages typically collapse to a single `other` category with no grammatical plural marking on the noun after a number, but this is stated as practitioner expectation, not a verified CLDR lookup, and joins the existing Uzbek/Russian localization items in Open Questions needing native-speaker sign-off. The concrete engineering action either way: use ICU MessageFormat (or an equivalent CLDR-aware pluralization library) from the first i18n commit, not string concatenation, so adding Russian's extra categories later isn't a rearchitecture.

**Design-system governance at scale.** The original report's "small pattern library" idea (borrowed from GOV.UK) needs an ownership answer before it survives contact with multiple sub-departments, let alone other ministries: one named owner (not a committee) per shared component, a lightweight versioning convention (a changelog per component, not per release of the whole app), and a rule that any sub-department or future tenant can *request* a new pattern but not silently fork an existing one — the same "one right way to do it" discipline the original report already praises in Linear, applied to the component library itself rather than only to product workflows.

### New verdicts (extending "What this means for us")

16. **[ADOPT]** A hard 5-item top-level IA (Overview, Work, People, Requests, Events) with three explicit disclosure tiers (default / one-click / power) and a per-user, reversible "show more tools" toggle — the concrete mechanism the original progressive-disclosure section named but never fully specified.

18. **[ADOPT]** Four parallel, linked onboarding checklists per newcomer (newcomer, manager, buddy, HR/admin), auto-generated from a role + sub-department template on hire-date entry, with one shared progress view for HR and the manager.
19. **[ADOPT]** A "?" contextual-help affordance on every screen (a short, task-scoped panel, not a help center) plus real example text in every input placeholder — Krug's "self-evident, then self-explanatory" ladder made concrete, and the actual replacement mechanism for tours.
20. **[ADOPT]** Shortcut hints rendered next to every menu item/tooltip that has one, plus a context-aware "?" keyboard-shortcut overlay and a one-time first-use tip toast — makes the keyboard path already recommended in Section 3 discoverable without prior knowledge.
21. **[ADOPT]** Per-category notification cadence (real-time / daily digest / weekly digest), with direct @mentions and a person's own escalations always bypassing batching, and a Monday-morning digest as the department-wide default.
22. **[ADOPT]** A persistent, keyboard-focusable toast paired with a polite ARIA live-region announcement for every Undo action — a live-region announcement alone is transient and cannot be reviewed, which would silently exclude screen-reader and keyboard users from the Undo pattern Section 4 recommends everywhere.
23. **[AVOID]** Percentage-only adoption dashboards as the primary read on a 23-person department — each person is worth roughly 4.3 percentage points; track named completion and short qualitative pulses instead, reserving percentages for cross-department or cross-ministry comparison once the tool scales.
24. **[ADAPT]** Duolingo's retention mechanics minus the gamification skin — keep "reduce friction," "lower difficulty for returning users," and "auto-filter notifications to protect attention"; drop streaks, badges, and leaderboards as inappropriate for mandatory government work software.
25. **[ADAPT]** ICU MessageFormat (or equivalent CLDR-aware pluralization) from the first i18n commit, specifically because Russian's four plural categories will silently render wrong text if the codebase assumes the two-category English pattern.
